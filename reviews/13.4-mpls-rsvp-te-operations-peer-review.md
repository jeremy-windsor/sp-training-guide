**Reviewer:** Senior SP Network Engineer (IE-SP lens)

## Grade: C+

The operational philosophy and troubleshooting methodology are solid — the "troubleshooting hierarchy" framework and incident playbooks are genuinely useful. But the document has significant CLI syntax errors, at least one fabricated RFC reference, contradictory capacity numbers, missing critical production topics, and several IOS-vs-XR conflation errors that would mislead someone preparing for a CCIE-SP or JNCIE-SP lab. A candidate who memorized the CLI in this doc would fail configuration tasks.

## CRITICAL ISSUES (Exam-flunking / Production-dangerous)

### 1. RFC Attribution Wrong — RFC 2961 for Refresh/Timeout Defaults (Lines ~72-78)

The timer table states:

> State refresh: 30s — standard per RFC 2961
> State timeout: 90s — 3× refresh rate, per RFC 2961

**Wrong RFC.** The 30-second refresh interval and 90-second state timeout (K_R = 3) are defined in **RFC 2205** (original RSVP specification), Section 3.7. **RFC 2961** is "RSVP Refresh Overhead Reduction Extensions" — it defines MESSAGE_ID, bundle messages, and summary refresh, not the base timers. A CCIE-SP examiner would mark this incorrect.

**Fix:** Change both references to RFC 2205.

---

### 2. IOS-XR RSVP Debug Syntax is Classic IOS (Lines ~173-184)

```
monitor session 1
 logging buffered 10000
!
logging monitor errors
debug rsvp errors
```

This is **classic IOS syntax**, not IOS-XR. In IOS-XR:
- `monitor session` is for SPAN/port-mirroring, not debug output.
- `logging buffered 10000` and `logging monitor errors` are IOS-style.
- IOS-XR debug is simply `debug rsvp error`, and output goes to syslog by default.

**Fix:** Replace with valid IOS-XR debug workflow:
```
debug rsvp error
# output goes to syslog; use:
show logging | include RSVP
# when done:
no debug rsvp error
```

### 3. IOS-XR BFD Config Under Wrong Hierarchy (Lines ~481-487, ~996-1003)

The document shows BFD configured under `mpls traffic-eng` → `tunnel`:

```
mpls traffic-eng
 tunnel <tunnel-id>
  bfd
   multiplier 3
   minimum-interval 50
```

**This is not valid IOS-XR syntax.** BFD on TE tunnels is configured under the **interface**:

```
interface tunnel-te1
 bfd fast-detect
  minimum-interval 50
  multiplier 3
```

Same error appears again in the FRR+BFD section (line ~996). Two occurrences of the same mistake.

---

### 4. RSVP Authentication Config — Wrong Hierarchy and Syntax (Lines ~367-381)

```
# IOS-XR
router rsvp
 interface GigabitEthernet0/0/0/0
  authentication md5 key-chain RSVP-KEY
```

**Two errors:**
1. IOS-XR RSVP config is under `rsvp`, not `router rsvp`.
2. The `authentication md5 key-chain` syntax is wrong. Correct syntax:

```
rsvp
 interface GigabitEthernet0/0/0/0
  authentication key-chain RSVP-KEY
```

The MD5 algorithm is specified in the key-chain itself, not in the RSVP authentication command.

Also, the key-chain syntax shown:
```
key chain RSVP-KEY
 key 1
  crypto algorithm md5
  key-string <secret>
```

Should be:
```
key chain RSVP-KEY
 key 1
  key-string <secret>
  cryptographic-algorithm HMAC-MD5
```

`crypto algorithm md5` is not valid IOS-XR key-chain syntax.

### 5. Contradictory Capacity Numbers (Lines ~453-457 vs ~1015-1030)

Section 5 says:

> A typical PE router reserves ~2 MB for RSVP sessions. At 10 KB per session, that's a ceiling of ~200 RSVP sessions.

Section 9 table says:

> ASR 9000: ~30,000 sessions

A 2 MB RSVP allocation is a **fabricated "typical" number** that's off by orders of magnitude. Modern PE routers allocate far more than 2 MB for RSVP. A Cisco ASR 9000 with 30,000 sessions at 10 KB each would need ~300 MB of state — 150× the claimed "typical" allocation. These sections directly contradict each other.

**Fix:** Remove or heavily qualify the "2 MB / 200 sessions" example. It's not representative of any modern SP platform.

### 6. `mplsTunnelOperTable` Doesn't Exist (Lines ~437-438)

```
mplsTunnelOperTable     — operational status
```

**This table does not exist in MPLS-TE-STD-MIB (RFC 3812).** Operational status is an object (`mplsTunnelOperStatus`) within `mplsTunnelTable`. There is no separate `mplsTunnelOperTable`. This would be marked wrong on any SNMP-focused exam question.

**Fix:** Remove the `mplsTunnelOperTable` line and note that `mplsTunnelOperStatus` is a column in `mplsTunnelTable`.

## MAJOR ISSUES (Wrong answers / Confusing)

### 7. Junos RSVP Traceoptions Flags — Fabricated (Lines ~187-191)

```
set protocols rsvp traceoptions flag path send
set protocols rsvp traceoptions flag path receive
```

**`path send` and `path receive` are not valid RSVP traceoptions flags on Junos.** Valid RSVP traceoptions flags include: `all`, `error`, `event`, `state`, `packet`, `packet-detail`, `normal`, `task`, `timer`. The correct approach to trace RSVP PATH messages would be:

```
set protocols rsvp traceoptions flag packet
set protocols rsvp traceoptions flag packet-detail
```

---

### 8. `show mpls traffic-eng tunnels | count Up` — Invalid IOS-XR Pipe (Line ~222)

IOS-XR does not have a `| count <string>` pipe option. The available pipes are `include`, `exclude`, `begin`, `section`, `file`. To count matching lines, you'd need:

```
show mpls traffic-eng tunnels | include Up | utility wc -l
```

Or on Junos: `show mpls lsp | match Up | count` (Junos does support `| count` but only without arguments).

---

### 9. `monitor mpls traffic-eng tunnels` — Fabricated Command (Line ~282)

This command does not exist in IOS-XR. The `monitor` keyword in IOS-XR is for SPAN sessions, not for "watching" TE tunnel state. To monitor tunnel state changes in real time on IOS-XR, you'd poll periodically or use telemetry subscriptions.

---

### 10. `tunnel-mpp` / `mpls oam interval` — Fabricated Config (Lines ~505-508)

```
mpls traffic-eng tunnels
 tunnel-mpp
  mpls oam interval 60
```

**`tunnel-mpp` is not a valid IOS-XR configuration stanza.** MPLS OAM in IOS-XR is configured under `mpls oam`:

```
mpls oam
```

And periodic LSP ping is not configured via an `interval` keyword under a `tunnel-mpp` hierarchy. This entire block appears fabricated.

---

### 11. Auto-Bandwidth Overflow Config — Fabricated Syntax (Lines ~838-849)

```
mpls traffic-eng
 auto-bw overflow
  minimum-overflow 2
!
tunnel-group 1
 auto-bw overflow
  minimum-overflow 2
```

**Neither block is valid IOS-XR syntax.**
- `auto-bw overflow` is not a standalone global command. Auto-bw overflow is configured **per-tunnel** under the tunnel-te interface.
- `tunnel-group` is not a valid IOS-XR configuration element in this context.

Correct syntax:
```
interface tunnel-te1
 auto-bw
  overflow threshold 10 min 50 limit 2
```

---

### 12. `fast-reroute protect node` — Not Valid IOS-XR (Line ~928)

```
mpls traffic-eng
 tunnel-te 1
  fast-reroute protect node
```

**`fast-reroute protect node` is not valid IOS-XR syntax.** In IOS-XR, FRR is enabled with just `fast-reroute` under the tunnel-te interface. Node vs. link protection is determined by what bypass tunnels are available, not by a sub-command. There is a `bw-protect` option, but not `protect node`.

```
interface tunnel-te1
 fast-reroute
```

This might be confused with classic IOS `tunnel mpls traffic-eng fast-reroute node-protect`.

---

### 13. `mpls traffic-eng reoptimize force-tunnel` — Wrong Keyword (Line ~700)

```
mpls traffic-eng reoptimize force-tunnel <tunnel-id>
```

**`force-tunnel` is not a valid keyword.** The correct IOS-XR command is:

```
mpls traffic-eng reoptimize tunnel <tunnel-number>
```

Or to reoptimize all tunnels: `mpls traffic-eng reoptimize`.

---

### 14. FRR Bypass Tunnel Config — Wrong IOS-XR Syntax (Lines ~913-919)

```
interface tunnel-te 100
 mpls traffic-eng
  backup-bw global-pool unlimited
  path-option 1 explicit name BYPASS-A-TO-C
```

Multiple issues:
- `mpls traffic-eng` is not a valid sub-mode under `interface tunnel-te` in IOS-XR.
- `backup-bw global-pool unlimited` looks like classic IOS syntax.
- Bypass tunnel path-options and backup-bw are configured directly under the interface:

```
interface tunnel-te100
 autoroute
 destination <next-next-hop>
 backup-bw global-pool <bandwidth>
 path-option 1 explicit name BYPASS-A-TO-C
```

But more importantly, **modern IOS-XR uses auto-tunnel bypass** — manual bypass tunnels are rarely configured. The document should mention this.

---

### 15. "Juniper MX (PTX)" — Different Product Lines (Line ~1020)

```
| Juniper MX (PTX) | ~100,000 | ~10,000 | Distributed signaling via RE/fabric |
```

**MX and PTX are completely different product lines.**
- MX Series: Universal edge/core routing platforms (MX240, MX480, MX960, MX10008, MX10016)
- PTX Series: Packet transport routers (PTX10001, PTX10004, PTX10008, PTX10016)

They have different RE architectures, different scale numbers, and different positioning. Listing them together as "MX (PTX)" is like saying "Cisco ASR (NCS)". Pick one or list both separately with their own numbers.

### 16. Junos BFD Syntax Error (Lines ~488-492)

```
set protocols mpls label-switched-path <lsp-name> bfd-liveness-detection \
    transmit-interval minimum-interval 50
```

**`transmit-interval minimum-interval` is not valid Junos syntax.** The correct keyword is `minimum-transmit-interval`:

```
set protocols mpls label-switched-path <lsp-name> bfd-liveness-detection \
    minimum-transmit-interval 50
```

### 17. `show mpls label` on Junos — Doesn't Exist (Line ~568)

```
show mpls label  # Junos
```

**This command does not exist on Junos.** To view MPLS labels on Junos, use:
```
show route table mpls.0
```

### 18. `show mpls lsp count terse` — Not Valid Junos (Line ~296)

```
show mpls lsp count terse
```

`count` and `terse` are separate display modifiers on Junos — you can't combine them this way. Use either:
```
show mpls lsp terse
show mpls lsp count
```

### 19. Junos `clear mpls lsp optimize` — Verify Syntax (Line ~1008)

```
clear mpls lsp optimize
```

On Junos, the command to trigger LSP reoptimization is:
```
request mpls optimize reassess
```
or
```
clear mpls lsp optimize-aggressive
```

`clear mpls lsp optimize` may not be valid. Verify against Junos version.

## MODERATE ISSUES (Accuracy / Completeness)

### 20. Reply Mode Descriptions Questionable (Lines ~241-246)

```
ping mpls ipv4 <destination-ip> 10.0.0.1/32 reply-mode router
ping mpls ipv4 <destination-ip> 10.0.0.1/32 reply-mode route-lookup
```

The `reply-mode` options `router` and `route-lookup` don't match IOS-XR command syntax. Actual IOS-XR reply modes include `ipv4` and `router-alert`. The functional descriptions are also misleading — the distinction between the two modes as described doesn't accurately reflect RFC 8029 behavior. The standard reply modes are:
- **1 (IPv4 UDP reply):** Default. Reply via UDP.
- **2 (Router Alert):** Reply via UDP with router alert IP option.
- **3 (MPLS label stack):** Reply with specified label stack.
- **4 (Control channel):** BFD/IPV6 mechanism.

---

### 21. RSVP Hello Default — Verify 9s on Both Platforms (Line ~69)

The table states hello interval defaults are 9s on both IOS-XR and Junos. While this is a commonly cited value, the actual default varies by platform and software version. On some IOS-XR platforms, RSVP hello may not be enabled by default. On Junos, RSVP hello behavior differs — Junos relies more heavily on RSVP refresh for neighbor detection. The document should note "verify against platform-specific documentation" rather than presenting these as universal defaults.

---

### 22. HMAC-SHA Attributed to RFC 2747 (Line ~328)

> RSVP-TE authentication exists (RFC 2747 INTEGRITY object, MD5/HMAC-SHA)

RFC 2747 defines HMAC-MD5 only. HMAC-SHA for RSVP is defined in **RFC 4230** ("RSVP Cryptographic Authentication"). Listing HMAC-SHA under RFC 2747 is incorrect.

## VERDICT

The document's **operational narrative and incident playbooks are strong** — those sections read like they were written by someone who has actually been paged at 2am for an RSVP storm. The problem is that nearly every CLI config block and show command has at least one error. The IOS-XR configs consistently mix classic IOS and IOS-XR syntax, and the Junos commands include several fabricated flags/options that don't exist.

**Required before this module is usable:**
1. Fix all 6 critical issues — these are exam-flunkers
2. Fix all 13 major CLI issues — these would break configs
3. Resolve the contradictory capacity numbers
4. Add auto-tunnel bypass as the modern IOS-XR approach
5. Separate MX and PTX platform numbers
