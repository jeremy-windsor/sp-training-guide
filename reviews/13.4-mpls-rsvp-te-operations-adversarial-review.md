# Adversarial Review: Module 13.4 — MPLS & RSVP-TE Operations at Scale

**Reviewer:** Adversarial (IE-SP lens)
**Date:** 2026-04-09

---

## Grade: C+

The module captures the operational vibe well and provides a great troubleshooting framework. However, critical technical inaccuracies in CLI syntax, default timers, and platform scaling would lead a student to fail a JNCIE-SP/CCIE-SP lab or cause production outages if followed literally.

---

## 1. Command Syntax & Logic Errors

- **IOS-XR Syntax Hallucinations:**
  - `mpls traffic-eng reoptimize` does not exist in this form in IOS-XR. Correct approach is via tunnel interface or toggling tunnel state.
  - `mpls traffic-eng reoptimize force-tunnel <tunnel-id>` — not a valid IOS-XR command.
  - `mpls traffic-eng tunnels brief | include FRR` — not standard syntax.
- **Junos Syntax Errors:**
  - `clear mpls lsp optimize` — correct Junos command is `clear mpls lsp name <name>`.
- **Logic Gap:** `ping mpls traffic-eng tunnel all` — no "all" keyword exists for this command in IOS-XR; must ping tunnels individually or script/YANG.

## 2. Timer & Default Value Inaccuracies

- **RSVP Hello Intervals:**
  - **Claim:** "Hello interval: 9s (IOS-XR/Junos)"
  - **Reality:** In modern IOS-XR and Junos, RSVP hellos are **disabled by default** unless Graceful Restart or specific hello-intervals are configured. When enabled, the default is typically **30 seconds**, not 9s.
- **Detection Time:** Claims 9s detection at the recommended interval. In reality, if interval is 3s and misses is 3, detection is 9s. But the "default" behavior without BFD is far slower.
- **Refresh Timers:** 90s "State timeout" default is generally correct per RFC 2205 (not 2961 as stated), but ignores that most production SPs tune these significantly.

## 3. RFC & Technical Accuracy

- RFCs (2205, 2961, 4090, 2747, 4379, 8029) are correctly matched to their functions.
- **FRR (Section 8):** Facility Backup vs. One-to-One behavior description is correct. But bypass tunnel config example lacks the specific `mpls traffic-eng backup` association commands required to bind the bypass to the protected link.

## 4. Platform Scale Fabrication

- **ASR 9000:** Claiming a limit of 3,000 LSPs is an extreme underestimate for modern ASR9K — can handle tens of thousands depending on memory.
- **NCS 5500:** "Distributed signaling" claim is misleading; RSVP-TE is predominantly handled by the control plane (CPU). FIB is distributed, but RSVP state machine is not "distributed across line cards."
- **Memory Claims:** "Typical PE router reserves ~2 MB for RSVP sessions" is arbitrary and doesn't correspond to any specific platform.

## 5. Operational Risks (Outage Potential)

- **Graceful Shutdown:** Setting IGP metric to max and waiting for convergence is correct, but then telling user to `shutdown` the interface without verifying all LSPs (including from other head-ends) have vacated the link risks hard drops.
- **Bypass Bandwidth Trap:** Section 8 mentions bypass bandwidth but doesn't emphasize that if the bypass tunnel lacks enough bandwidth, FRR switchover will fail or cause massive drops during the most critical moment.

## 6. Missing Critical Topics (NEW — not in peer review)

- **LDP-IGP Synchronization:** No mention of LDP-IGP sync, which is the #1 cause of black holes during the "Bring-Back Procedure" described in Section 3.
- **Label Range Partitioning:** Guide mentions label space but ignores the label range conflict where RSVP and LDP might compete for the same range if not explicitly partitioned.
- **Make-Before-Break (MBB) Internals:** Mentions MBB but never explains how it works or how to troubleshoot a "stuck" MBB session — a common production issue.
