# Peer Review: Module 13.3 — SRv6 Security

**Reviewer:** Senior SP Network Engineer (CCIE/CCDE Level)
**Date:** 2026-04-07
**Module Grade: B+**

## Executive Summary
The module is technically strong and provides an "honest" look at SRv6 security, moving beyond marketing fluff. It correctly identifies the fundamental architectural risk (SRv6 is just IPv6) and maps the RFC 8754 trust model to operational reality. The attack scenarios are well-chosen and relevant for an IE-level candidate.

However, there are minor technical inaccuracies regarding specific RFC sections and a few CLI nuances that could lead a student to fail in a real lab or exam environment. The grade is a B+ because while the conceptual depth is A+, the technical precision on the "fine print" is B.

---

## Detailed Findings

### 1. Wrong Syntax & Vendor Claims
- **IOS-XR ACLs:** The module notes that `routing-type` is hardware-dependent. This is correct. However, in the provided `SRV6_DOMAIN_BOUNDARY_INBOUND` ACL, line 20 (`deny ipv6 any fc00::/32`) is a standard prefix match. This is production-safe. But the `SRV6_PER_NODE_INBOUND` ACL uses `routing-type 4`. On many NCS5500/ASR9K platforms, matching extension headers in a standard IPv6 ACL requires specific `ipv6 extension-header` keywords or is only supported in specific "advanced" ACL modes. The module should explicitly warn that `routing-type` may not be a valid keyword in all XR versions (e.g., 6.x vs 7.x).
- **Junos Filters:** The use of `extension-header routing-header` and `routing-header-type 4` is accurate for Trio-based MX. The warning about EX/QFX is critical and correctly included.

### 2. Fabricated/Incorrect Facts & RFC References
- **RFC 8754 §5.1:** The module repeatedly references §5.1 for the trust boundary model. This is accurate.
- **RFC 8754 §7.5 (AH Compatibility):** The module claims AH is not compatible because the Destination Address (DA) and Segments Left (SL) are mutable. **Correction:** While the conclusion (AH is incompatible) is correct, the reasoning is slightly off. AH *can* handle mutable fields by zeroing them out during the HMAC calculation. The actual incompatibility is that SRv6 segment endpoints *modify* the DA to a value that was not the original DA. This breaks the integrity check at the *next* hop because the previous node's modification isn't "transparent" in the way AH expects.
- **RFC 9602 Reference:** The module references RFC 9602 for SID block design. RFC 9602 is an *Informational* RFC (October 2024) and provides guidance, but not normative requirements. The module treats it as a standard; it should be clarified as informational.

### 3. Copy-Paste & Self-Referential Errors
- **Scenario 4 (Transit Nodes):** The text mentions "the CoPP section above" before the CoPP section actually appears in the document. This is a self-referential error (forward reference instead of back reference).
- **Terminology:** Consistency is good. "SID block" and "locator block" are used interchangeably; while common in the industry, for an IE-level guide, they should be strictly defined once and then kept consistent.

### 4. Missing Edge Cases & Incomplete Sections
- **SIDs in the Payload:** The module misses the "SRv6-in-UDP" (RFC 8754 §6) security implication. If SRv6 is encapsulated in UDP (to help with ECMP and firewall traversal), the boundary filters must be updated to inspect the UDP payload, or the firewall is blind. This is a major real-world gap.
- **uSID Opacity:** The section on uSID mentions it is "harder to inspect." It should explicitly mention that since multiple SIDs are packed into one address, a simple prefix-based ACL (`deny ipv6 any fc00::/32`) might still work, but *per-SID* filtering becomes almost impossible without deep packet inspection.

### 5. Grade-Level Appropriateness (IE-SP)
- **Depth:** The level is appropriate. It doesn't just explain *how* to configure it, but *why* the architecture is vulnerable.
- **Review Questions:** The questions are excellent. Question 1 (customer-facing SRv6) and Question 5 (internal compromise) are exactly the kind of "scenario-based" thinking required for the IE exam.
- **SR-MPLS vs SRv6 Comparison:** Fair, accurate, and refreshingly honest. It correctly identifies that SR-MPLS's security is a byproduct of its label-space isolation.

---

## Final Assessment

### Production-Safe ACLs?
**Yes.** The destination-based filtering (`deny ipv6 any [SID_BLOCK]`) is the gold standard for SRv6 boundary protection and is safe to deploy.

### IE-Level Appropriateness?
**Yes.** The complexity of the attack scenarios and the focus on RFC-level nuances (like AH incompatibility) align with IE expectations.

### Recommendation
**Approve with Minor Edits.**
1. Move the "CoPP section" before it is referenced in Scenario 4.
2. Add a brief note on SRv6-in-UDP security implications.
3. Refine the AH explanation to emphasize that the *modification* of the DA by the endpoint is the breaking point, not just that the field is mutable.
