## 2. Remaining Issues

### CRITICAL — Junos Source Prefix-List Uses Wrong Prefix

**Location:** Lines 378-381, Junos iACL section

**The problem:** The Junos `SRV6_DOMAIN_SOURCES` prefix-list contains `fc00::/32` — the SID block. The IOS-XR equivalent was correctly changed to infrastructure addressing (`2001:db8:infra::/48`, `2001:db8:loopbacks::/48`) with an explicit NOTE explaining why the SID block must NOT be used as the source authorization space. The Junos example was not updated.

```
policy-options {
    prefix-list SRV6_DOMAIN_SOURCES {
        fc00::/32;          ← BUG: This is the SID block, not infrastructure addresses
    }
```

This is the exact bug the adversarial review flagged as "the source-authorization logic is wrong for RFC 8754 per-node protection." It was fixed in IOS-XR but missed in Junos. A reader copy-pasting the Junos example authorizes SRH traffic sourced from the SID block — which an attacker can forge.

**Fix:** Change to infrastructure prefixes matching the IOS-XR example:
```
prefix-list SRV6_DOMAIN_SOURCES {
    2001:db8:infra::/48;
    2001:db8:loopbacks::/48;
}
```

### SIGNIFICANT — Junos Example Missing Destination-Based Boundary Filter

**Location:** Junos iACL section (around line 384)

**The problem:** The module's core thesis — stated repeatedly and correctly — is that **destination-based SID block filtering is the primary control** per RFC 8754 §5.1. The IOS-XR section has two ACLs:
1. `SRV6_DOMAIN_BOUNDARY_INBOUND` — destination-based (`deny ipv6 any fc00::/32`)
2. `SRV6_PER_NODE_INBOUND` — SRH-type-based with source validation

The Junos section only has one filter: `SRV6_IACL_INBOUND`, which matches on `extension-header routing-header; routing-header-type 4`. This is the per-node SRH-type filter. **There is no Junos destination-based boundary filter.**

This means the Junos example fails to implement the module's own primary recommendation. Single-segment no-SRH traffic (the attack surface covered in the new dedicated section) passes through the Junos filter completely — because it doesn't match on SRH.

**Fix:** Add a Junos destination-based boundary filter, or add a destination-prefix-list term to the existing filter:
```
term DENY_SID_BLOCK_FROM_EXTERNAL {
    from {
        destination-prefix-list {
            SRV6_DOMAIN_SIDS;
        }
    }
    then {
        discard;
        count SID_BLOCK_DROPS;
        syslog;
    }
}
```
Place this before the PERMIT_SRV6_FROM_DOMAIN term.

### SIGNIFICANT — Comparison Table "Injection Attack Surface" Row Contradicts Itself

**Location:** SRv6 vs SR-MPLS comparison table

| Aspect | SR-MPLS | SRv6 | Winner |
|--------|---------|------|--------|
| **Injection attack surface** | Lower barrier: requires MPLS access, but MPLS-over-UDP (RFC 7510) and MPLS-over-GRE reduce this to IP reachability | Lower barrier: requires only IPv6 reachability to SID block | SR-MPLS (narrower default, not immune) |

**Problem:** Both cells say "Lower barrier." For SR-MPLS, requiring MPLS access is a *higher* barrier than requiring IPv6 reachability. The cell text says the barrier has been *lowered* by encapsulation, but the phrasing reads as "both have lower barriers" — which muddies the comparison. The Winner column correctly says "narrower default, not immune," which contradicts the "Lower barrier" cell text.

**Fix:** Rewrite the SR-MPLS cell to contrast more clearly:
```
| Higher barrier for native MPLS (requires MPLS domain access);
  MPLS-over-UDP (RFC 7510) and MPLS-over-GRE narrow this gap |
  Lower barrier: requires only IPv6 reachability to SID block |
  SR-MPLS (narrower default, not immune) |
```

### MODERATE — Scenario 6 Inline ACL Syntax

**Location:** Line 284

```
`ipv6 access-list BLOCK_FRAGMENTS: deny ipv6 any any fragments` (IOS-XR)
```

**Problem:** The colon-separated one-liner is not valid IOS-XR syntax. In IOS-XR, ACLs are defined as multi-line blocks:
```
ipv6 access-list BLOCK_FRAGMENTS
  10 deny ipv6 any any fragments
```

The `fragments` keyword itself is correct for matching IPv6 fragmented packets. The issue is the presentation format, which could mislead someone into thinking this is a valid single-line IOS-XR command.

**Fix:** Present as a proper config block or add "(syntax simplified for readability)" note.

### MODERATE — BGP SR Policy Draft Reference May Be Outdated

**Location:** Lines 938, 980

```
BGP SR Policy (draft-ietf-idr-segment-routing-te-policy) distributes SR Policies via BGP.
```

This reference appears twice. If draft-ietf-idr-segment-routing-te-policy has been published as an RFC by 2026 (it was well along in the IETF process as of 2023-2024), the module should reference the RFC number, not the draft name. For IE-level training material referencing a specific protocol mechanism, the citation should use the most current standards track document.

**Fix:** Verify publication status. If published as an RFC, update both references. If still a draft, add "(currently an IETF draft)" for clarity.

### MODERATE — RFC 9602 for uSID Needs Verification

**Location:** Line 910

```
uSID (RFC 9602 §3) compresses multiple SIDs into a single 128-bit IPv6 address
```

RFC 9602 is referenced as "SRv6 SID Allocation." If §3 of RFC 9602 specifically describes the uSID compression format, the reference is correct. However, the primary compressed SID specification was developed in `draft-ietf-spring-srv6-sid-compressed` — if that became a different RFC, the uSID reference here might point to the wrong document. The cross-reference at the bottom says only "RFC 9602 (SRv6 SID Allocation)" without mentioning uSID specifically.

**Fix:** Verify that RFC 9602 §3 is indeed the authoritative reference for uSID compression behavior. If uSID is defined in a different RFC, correct the reference.

### MINOR — RFC 9343 for GUE Needs Verification

**Location:** Line 809

```
RFC 9343 defines SRv6 over GUE
```

Needs verification that RFC 9343 is the correct RFC number for SRv6 over Generic UDP Encapsulation. If the GUE encapsulation for SRv6 specification received a different RFC number, this reference is wrong.

### MINOR — SID Block Notation Inconsistency

**Location:** Various ACL examples

The SID block is written as both `fc00::/32` and `fc00:0::/32` in different ACL examples. While semantically equivalent, the inconsistency can confuse readers who are comparing examples side by side.

**Recommendation:** Pick one notation and use it consistently throughout. The shorter `fc00::/32` is fine.

---

### MINOR — RFC 6980 Cross-Reference Scope

**Location:** Cross-reference section at end

```
RFC 6980 (Security Implications of IPv6 Fragmentation — relevant to Scenario 6)
```

RFC 6980 is specifically about IPv6 fragmentation interaction with IPsec AH ("Security Implications of IPv6 Fragmentation with the IPv6 Authentication Header"). It's relevant to the fragmentation discussion but a reader expecting a general IPv6 fragmentation security treatment will get something narrower. A more general reference like RFC 8200 §4.5 (IPv6 fragmentation specification) might be a better companion.

## 3. New Content Quality Assessment

### Single-Segment SRv6 Section — Rating: Excellent

This is the most important addition. The section correctly identifies that RH4 filtering alone is insufficient and provides the clearest explanation I've seen in training material of why destination-based SID block filtering is the universal control. The filter coverage table is a great quick-reference.

One minor note: the table's "GUE/UDP port filter" row says "Encap-specific" for coverage. This is accurate — it catches both SRH and no-SRH traffic *within the encapsulated path* but doesn't cover native SRv6. Could add a footnote for clarity.

### Inter-Domain and Multi-AS Section — Rating: Good

Technically sound. The stitching SID discussion and End.B6.Encaps as security gateway model is correct. The four practical recommendations are actionable.

One gap: the section references Inter-AS Option C (RFC 4364 §10) for context but doesn't discuss how SRv6-specific the Option C equivalent is. In MPLS Option C, labels are exchanged between ASes. In SRv6 Option C, it's locators/SIDs. The security implications differ because SIDs are routable IPv6 addresses. This nuance could be made more explicit.

### Extension Header Chain Evasion — Rating: Very Good

The mechanism description is correct. The key insight — that destination-based filtering catches what EH matching misses due to parser depth limits — is clearly stated and directly supports the module's thesis.

The mitigation section references RFC 9288 and platform-specific knobs. The Junos reference to `ba-led-ingress-limits` should be verified — this is a platform-specific knob that may not be the right one on all Trio generations.

### Control-Plane Attack Surface — Rating: Good

Covers IGP locator poisoning, BGP SR Policy abuse, and compromised internal headends. The internal headend section correctly identifies that this is a fundamentally different threat than external injection and references RFC 8754 §5.2's delegated validation model.

### SID Behavior Risk Hierarchy — Rating: Very Good

Clear, actionable, and prioritized correctly. End.DT* and End.B6* at Critical is right. The operational takeaway is practical.

### Firewall Deep Inspection — Rating: Excellent

Directly addresses the prior review's finding that "chasing the segment list" is insufficient. The three points about why segment list alone doesn't determine outcome are correct. The practical guidance (SRv6-aware vs. fail-closed) is the right operational framing.

### Fragmentation Filtering Tradeoffs — Rating: Very Good

Balanced treatment. The recommendation to validate PMTUD before blanket fragment drops is practical. The monitoring advice (watch for TCP retransmissions after enabling) is the kind of detail that separates training material from documentation.

### New Review Questions 6 and 7 — Rating: Excellent

Q6 (inter-AS SRv6 with End.B6.Encaps stitching) is a well-constructed IE-level question that tests three distinct knowledge areas in one prompt. Q7 (EH chain evasion vs. DA-based filtering) directly tests the most important architectural insight in the module.
