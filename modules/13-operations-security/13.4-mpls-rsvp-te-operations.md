## Overview

> The design document says RSVP-TE tunnels carry 80 Gbps. The 2am page says three LSPs are down, two are suboptimal, one is flapping, bandwidth reservations are out of sync on five transit nodes, and the customer-facing VRF on PE3 has a black hole because LDP neighbor adjacency dropped during a core-side IGP flap that no one noticed. This section covers how to keep RSVP-TE from becoming the root cause of your worst outages — not how to design it (that's Module 5), but how to run it, monitor it, debug it, and survive the inevitable incidents at production scale.

**What you'll learn:**
- The RSVP state machine and what each state transition tells you in production
- Systematic troubleshooting methodology for RSVP-TE tunnel failures (LSP down, suboptimal, flapping, degraded)
- Maintenance procedures that don't cause cascading failures (graceful shutdown, make-before-break validation, cutover strategies)
- Security threats to RSVP-TE — LSP hijacking, label spoofing, resource exhaustion, and how to defend
- Monitoring architecture: what to track, how to detect degradation before customers notice, YANG paths for streaming telemetry
- Incident response playbooks: LSP down, mass preemption, label table exhaustion, RSVP adjacency loss
- Scale realities: RSVP state limits, LSP count ceilings, and what happens when you push past them

**Assumptions:** This section assumes RSVP-TE is already deployed and designed (Module 5). We are building the operational layer — monitoring, troubleshooting, security hardening, and incident response for an RSVP-TE transport network carrying production traffic at scale.

## 1. RSVP State Machine — What States Mean in Production

### The Fundamental State Machines

RSVP-TE has three critical state machines that you need to understand simultaneously:

#### RSVP-TE LSP State Machine (Head-End View)

```
              Down
               │
               ├─ CSPF computation succeeds → Admin Up / Path Sent
               │                              │
               │                              ├─ RESV received → Up (Active)
               │                              │
               │                              ├─ PathErr received → Path Error
               │                              │                      │
               │                              │                      ├─ Admin Down (if no retry)
               │                              │                      └─ Path Sent (retry)
               │                              │
               │                              └─ ResvErr → Resv Error → Up (if recoverable)
               │                                                        or Down
               │
               └─ Administrative actions ──┐
                                           ├─ admin-down → Down (clean teardown, PathTear/ResvTear sent)
                                           ├─ admin-standby → Standby (signaled but not forwarding)
                                           └─ standby-to-active → Up (via MBB or explicit switch)
```

#### RSVP Session State Machine (Per-Node View)

Every RSVP-enabled router maintains per-session state for each LSP that traverses it:

```
Path State Machine (forward direction, head → tail):
  NoPath → Path → PathError → (retry) → Path

Resv State Machine (reverse direction, tail → head):
  NoResv → ResvInit → Resv → ResvError → Resv → (cleanup) → NoResv
```

#### Operational Implication

The head-end tracks one state (the tunnel state). But there are N routers between head and tail, each with two state machines (Path and Resv), and failures can manifest differently at different points. When an LSP is "Down," the first question is not "why is the tunnel down." The first question is: "which router, which state machine, and which transition failed?"

### Production State Diagnostics

| State | What It Means | Where to Look First |
|-------|---------------|---------------------|
| **Down** | LSP is not signaled | CSPF failure, no IGP adjacency, bandwidth unavailability |
| **Admin Down** | Administratively disabled | Intentional, no action needed |
| **Path Error** | PATH message reached failure point, PathErr returned | Check PathErr code/reason on head-end |
| **Resv Error** | RESV message failed on reverse path | Check bandwidth availability, policy on failed node |
| **Up (Suboptimal)** | LSP is up but taking longer path than expected | CSPF using constrained metric, explicit path drift |
| **Up (Degraded)** | LSP is up but bandwidth reservation failed | Soft preemption, over-subscription, or policy rejection |
| **Flapping** | LSP cycles between Up and Error states | Unstable IGP, intermittent link, MTU mismatch, or timer thrashing |
| **Standby** | Backup LSP is signaled but inactive | Expected behavior for FRR/backup tunnels |

### State Machine Timing — Why It Matters

RSVP-TE timers control how quickly the network detects and responds to failures:

| Timer | IOS-XR Default | Junos Default | Production Recommendation |
|-------|---------------|---------------|---------------------------|
| **Hello interval** | 9s | 9s | 3s on critical links (67% reduction in detection time: 27s → 9s) |
| **Hello misses** | 3 | 3 | 3 (9s detection at recommended interval) |
| **State refresh** | 30s | 30s | 30s (standard per RFC 2961 — don't change) |
| **State timeout** | 90s | 90s | 90s (3× refresh rate, per RFC 2961) |
| **Path error retry** | 3 retries, 30s interval | 3 retries, 30s interval | Vendor default is usually fine |

**Critical insight**: RSVP-TE hello is a local link protocol. It detects loss of RSVP adjacency with your directly connected neighbor. It does NOT detect end-to-end LSP liveness. End-to-end LSP monitoring requires BFD or MPLS OAM (covered below).

## 2. Systematic Troubleshooting Methodology

### The Troubleshooting Hierarchy

Always troubleshoot in this order. Skipping levels causes you to chase symptoms at the wrong layer.

```
Level 0: Is the tunnel administratively up?
  ↓
Level 1: Is IGP reachable (head-end to tail-end, both directions)?
  ↓
Level 2: Is CSPF succeeding (path computed with constraints)?
  ↓
Level 3: Is PATH signaling reaching the tail (forward path)?
  ↓
Level 4: Is RESV signaling reaching the head (reverse path)?
  ↓
Level 5: Is data plane forwarding (labels installed, CEF programming)?
  ↓
Level 6: Is traffic flowing (end-to-end ping with MPLS label stack)?
```

#### Level 0: Administrative State

```
# IOS-XR
show mpls traffic-eng tunnels <tunnel-id> | include State
show mpls traffic-eng tunnels name <tunnel-name>

# Junos
show mpls lsp name <lsp-name> | match "State|Current"
show mpls lsp ingress name <lsp-name> detail
```

**Common issue**: Tunnel stuck in Admin Down after a maintenance window because someone forgot to re-enable it. Check `show logging` for the last administrative shutdown event.

#### Level 1: IGP Reachability

```
# IOS-XR
show isis adjacency  (or show ospf neighbor)
show isis route <tail-end-loopback>
show route <tail-end-loopback>

# Junos
show isis adjacency  (or show ospf neighbor)
show route <tail-end-loopback>
```

**Common issue**: IGP adjacency up, but loopback not in routing table due to route filtering, route leaking problems, or area boundary misconfiguration. Always check the actual route, not just the adjacency.

#### Level 2: CSPF Computation

```
# IOS-XR
show mpls traffic-eng topology
show mpls traffic-eng topology path <source-ip> to <dest-ip> \
    bandwidth <bw-kbps> affinity <affinity-mask>

# Junos
show ted database  (TE topology database)
show ted database extensive  (per-link reservable bandwidth, admin groups)
show mpls lsp ingress name <lsp-name> detail  (CSPF path computation result)
```

**CSPF failure modes:**

1. **No bandwidth available**: Every link in the IGP topology has insufficient reservable bandwidth for the requested amount. Check `show mpls traffic-eng topology` — look for links where "Reserved BW" equals "Max Res BW."
2. **Affinity/constraint mismatch**: The tunnel's affinity attributes don't match any available path. Check link attribute flags against tunnel affinity mask.
3. **Excluded resources**: Explicit path includes a downed link, or exclude-any list overlaps with all available paths.
4. **TED not synchronized**: IGP has advertised TE extensions, but TED hasn't converged yet. Check TED age versus IGP LSA age.
5. **Metric ceiling**: IGP metric to destination exceeds tunnel's `metric ceiling` configuration (tunnel won't use paths above the configured metric).

#### Level 3: PATH Signaling

When PATH message fails to reach the tail:

```
# IOS-XR — check PATH state on each hop
show rsvp neighbors
show rsvp session <tunnel-id> detail | include PATH|Down|Error
show rsvp neighbor <neighbor-ip> detail

# Junos
show rsvp neighbor
show rsvp session ingress name <lsp-name> detail
```

**PATH failure diagnostics:**

Run RSVP debug in production (carefully):

```
# IOS-XR — rate-limited RSVP debug
monitor session 1
 logging buffered 10000
!
logging monitor errors
debug rsvp errors
!
# After capturing, IMMEDIATELY:
no debug all
```

On Junos, enable traceoptions at the protocol level:

```
set protocols rsvp traceoptions file rsvp.log
set protocols rsvp traceoptions flag path send
set protocols rsvp traceoptions flag path receive
set protocols rsvp traceoptions flag error
```

**Common PATH failures:**
- RSVP not enabled on an interface along the path
- ACL blocking RSVP protocol (IP protocol 46)
- MTU mismatch on a transit link (Path messages can't fit)
- RSVP hello adjacency down on a specific hop

#### Level 4: RESV Signaling

When RESV message fails on reverse path:

```
# IOS-XR
show rsvp session <tunnel-id> detail | include RESV|Error|preempt
show rsvp session history  # historical reservation states

# Junos
show rsvp session egress name <lsp-name> detail
show rsvp session transit detail
```

**Common RESV failures:**
- Insufficient bandwidth at a transit node (bandwidth already allocated to other tunnels or IGP traffic reserves a percentage)
- Admission control policy rejecting the reservation
- Preemption: higher-priority tunnels preempted this tunnel's bandwidth
- Policy-based reservation rejection (e.g., CAC — Call Admission Control rejecting based on configured limits)

**The bandwidth preemption trap**: If Tunnel-A (priority 7) is preempted by Tunnel-B (priority 3), Tunnel-A goes down. But if Tunnel-A carries customer traffic, the customer sees an outage. Preemption is technically correct RSVP behavior but operationally catastrophic. The fix is not to avoid preemption — it's to design priority assignments so that the tunnels that actually carry customer traffic can't be preempted.

#### Level 5: Data Plane Programming

```
# IOS-XR
show cef mpls forwarding | include <tunnel-label>
show mpls forwarding | include <tunnel-label>
show mpls forwarding detail  # check for label programming errors

# Junos
show route protocol mpls
show route table mpls.0
show pfe route mpls label <label>
```

**Data plane failure modes:**
- Labels not programmed into CEF/FIB despite RSVP signaling succeeding
- PHP (Penultimate Hop Popping) stripping the wrong label
- Label space exhaustion (running out of local labels)
- Label conflict between LDP-allocated and RSVP-allocated labels

#### Level 6: End-to-End Data Plane Validation

```
# IOS-XR — MPLS ping and trace
ping mpls traffic-eng tunnel <tunnel-id>
traceroute mpls traffic-eng tunnel <tunnel-id>
ping mpls ipv4 <destination-ip> 10.0.0.1/32 reply-mode router
ping mpls ipv4 <destination-ip> 10.0.0.1/32 reply-mode route-lookup

# Junos
ping mpls lsp name <lsp-name>
traceroute mpls lsp name <lsp-name>
```

**Reply modes matter:**
- `reply-mode router`: The destination router confirms it has a route back to the source. This validates end-to-end reachability.
- `reply-mode route-lookup`: The destination router performs a route lookup for the source address. This detects asymmetric routing where the return path is broken.
- If MPLS ping succeeds but `reply-mode route-lookup` fails: the forward path works but the return path doesn't. Classic symptom of asymmetric IGP routing or VRF route leaking issues.

## 3. Maintenance Procedures That Don't Cause Cascading Failures

### The Maintenance Window Playbook

Every RSVP-TE maintenance operation should follow this checklist. Deviating from it is what causes 3am incidents.

#### Pre-Maintenance: Baseline Capture

```
# 1. Capture current LSP status
show mpls traffic-eng tunnels > pre-maint-tunnels.txt
show rsvp session > pre-maint-rsvp.txt
show rsvp neighbors > pre-maint-neighbors.txt
show mpls forwarding > pre-maint-labels.txt

# 2. Capture tunnel inventory (count by state)
# IOS-XR
show mpls traffic-eng tunnels | count Up
show mpls traffic-eng tunnels | count Down
show mpls traffic-eng tunnels | count "Path Err"

# 3. Capture auto-bandwidth history (for post-maintenance comparison)
show mpls traffic-eng tunnels auto-bw > pre-maint-ab.txt
```

**Save these files somewhere persistent.** Not just the router's buffer. Export to a server. When something goes wrong during maintenance, having a pre-state baseline is the difference between 5 minutes of diagnosis and 2 hours of wild guesses.

#### Graceful Shutdown Procedure

Never just `shutdown` an RSVP-enabled interface. Use the graceful shutdown sequence:

```
# Step 1: Set IGP overload to drain traffic away from this node/link (IOS-XR)
router isis 1
 interface GigabitEthernet0/0/0/0
  address-family ipv4 unicast
   metric maximum
  !
 !
!
# Wait for IGP convergence (traffic drains via alternate paths)
# Then check that RSVP-TE tunnels have re-signaled away from this interface:
show mpls traffic-eng fast-reroute database | include <interface>

# Step 2: Once LSPs have rerouted, shut the interface cleanly
interface GigabitEthernet0/0/0/0
 shutdown
!
# This triggers:
# 1. RSVP PATH_TEAR for any remaining LSPs using this interface
# 2. RSVP RESV_TEAR in reverse direction
# Head-ends that haven't already rerouted will recompute CSPF and re-signal
```

On Junos:

```
set protocols rsvp interface ge-0/0/0.0 disable
commit
# Wait for LSPs to reroute:
show mpls lsp | match "Down|Error"
# Confirm all LSPs have rerouted, then:
set interfaces ge-0/0/0 disable
commit
```

**Wait for LSP migration:** After initiating graceful shutdown, wait for all LSPs to successfully re-signal before proceeding with physical maintenance. Monitor:

```
# IOS-XR — watch LSPs reroute in real time
monitor mpls traffic-eng tunnels
# Or periodically check:
show mpls traffic-eng tunnels | count "Path Sent"
# When count is 0, all LSPs have been re-signaled

# Junos
show mpls lsp count terse
# Look for decreasing "Down" count, stable "Up" count
```

**Recommended wait time:** 2–5 minutes after graceful shutdown initiation. Large networks with hundreds of LSPs may need more.

#### Bring-Back Procedure

```
# Step 1: Enable IGP first (interface up, IGP adjacencies form)
# Step 2: Enable RSVP on interface
# Step 3: Wait for RSVP hello adjacency to come up
# Step 4: Verify TED has updated with new TE link
# Step 5: Wait for LSP optimization (auto-optimization interval or manual trigger)
```

IOS-XR:

```
interface GigabitEthernet0/0/0/0
 no shutdown
!
router rsvp
 interface GigabitEthernet0/0/0/0
  no shutdown
 !
!
# Verify
show rsvp neighbor | include <neighbor-ip>
show mpls traffic-eng topology | include <interface>
# Trigger LSP optimization if needed:
mpls traffic-eng reoptimize
```

**The TED convergence trap:** After an interface comes back, IGP converges first, RSVP discovers the neighbor, then the TE LSA floods and the TED updates. LSPs won't automatically re-optimize onto the restored link until the next auto-optimization cycle (default: 1 hour) or until manual reoptimize is triggered. Always run `mpls traffic-eng reoptimize` after maintenance restoration, or configure `mpls traffic-eng reoptimize timers delay` to trigger it automatically.

### LSP Cutover Validation

After any cutover (whether due to maintenance or incident recovery):

```
# Validate every tunnel:
# 1. Tunnel state matches pre-maintenance baseline
# 2. Labels are identical or correctly updated
# 3. Bandwidth reservations match expected values

# The single most important post-cutover check:
ping mpls traffic-eng tunnel all
# This validates every LSP in one command. If any fail, drill down:
show mpls traffic-eng tunnels | count Down
```

**Red flag:** If the post-cutover LSP count is lower than pre-cutover, something failed to re-signal. Do NOT close the maintenance window until the counts match. A tunnel that's "down" during maintenance is expected. A tunnel that's "down" after maintenance is an unresolved incident.

## 4. Security Threats to MPLS & RSVP-TE

### The Threat Model

MPLS and RSVP-TE have a fundamental security characteristic that is different from both SR-MPLS and SRv6:

**MPLS has no native encryption. RSVP-TE authentication exists (RFC 2747 INTEGRITY object, MD5/HMAC-SHA) but is rarely deployed at scale.** Both IOS-XR and Junos support per-interface RSVP MD5 authentication, and it works for point-to-point adjacency protection. However, in production SP networks with thousands of RSVP-TE sessions across hundreds of routers, authentication is typically limited to peering/edge interfaces due to operational overhead: key rotation, per-neighbor configuration management, and CPU overhead on high-session-count transit nodes.

The practical security model of MPLS/RSVP-TE is therefore predominantly perimeter-based: trust the core, authenticate at trust boundaries, filter at the edge, control who can inject packets into the MPLS domain, and monitor for anomalous behavior. If an attacker reaches the MPLS core control plane without traversing an authenticated boundary, they have significant leverage.

### Attack Vectors and Defenses

#### 1. LSP Hijacking via RSVP Spoofing

An attacker who can inject RSVP messages onto the control plane can:

- **Create unauthorized LSPs**: Signal new tunnels that consume bandwidth or change traffic patterns
- **Modify existing LSPs**: Send modified PATH messages to redirect LSPs through attacker-controlled paths
- **Tear down LSPs**: Send PATH_TEAR/RESV_TEAR to disrupt legitimate tunnels

**How it works in practice:**
```
Attacker → (injects RSVP PATH to PE2 as if from PE1) → 
PE2 processes PATH, sends RESV back to PE1 → 
PE1 receives RESV for a tunnel it didn't request →
PE1 may install forwarding state based on attacker-controlled path
```

**Defenses:**
- **LDP and RSVP authentication**: Use MD5 authentication for LDP adjacencies (IOS-XR: `md5 auth`, Junos: `authentication md5`). This is a basic control-plane hardening step — it doesn't require per-session secrets since LDP adjacency is point-to-point.
- **RSVP authentication** (rarely deployed): If you must deploy RSVP integrity, use it on peering links only (where you trust the other side anyway, so it's mostly for compliance). Configure via:
  ```
  # IOS-XR
  router rsvp
   interface GigabitEthernet0/0/0/0
    authentication md5 key-chain RSVP-KEY
   !
  !
  
  key chain RSVP-KEY
   key 1
    crypto algorithm md5
    key-string <secret>
  ```
- **Physical/port security**: The most effective defense. RSVP runs on directly connected interfaces. If an attacker can reach your RSVP adjacency, your physical security has already failed.
- **Control-plane policing**: Rate-limit RSVP protocol traffic on all interfaces:
  ```
  # IOS-XR — CoPP for RSVP
  class-map match-any RSVP-CONTROL
   match protocol rsvp
   end-class-map
  !
  policy-map input COPP-RSVP
   class RSVP-CONTROL
    police rate 100 pps
    !
  ```

#### 2. Label Spoofing and LSP Injection

Unlike SR-MPLS (where SIDs are globally routable) or SRv6 (where SIDs carry IPv6 addressing), MPLS labels are locally significant. This limits the label spoofing attack surface:

- Labels must be learned via LDP, RSVP-TE, or static configuration
- A valid label entry on one router doesn't translate to valid forwarding on another router without label distribution

**However:** If an attacker achieves routing protocol compromise (IGP or BGP), they can influence label distribution indirectly by:
- Advertising fake routes that LDP allocates labels for
- Influencing CSPF to include compromised nodes in LSP paths
- Manipulating TE topology advertisements

**Defense:** IGP/BGP authentication is the primary defense here. If your IGP can be compromised, RSVP-TE is the least of your problems.

#### 3. Resource Exhaustion via RSVP Flooding

An attacker who can reach RSVP-speaking interfaces can flood RSVP messages, consuming:
- RSVP session state memory (each RSVP session consumes ~10 KB of state)
- CPU cycles for RSVP message processing
- MPLS label space (each LSP requires label allocation)

**Impact calculation:** A typical PE router reserves ~2 MB for RSVP sessions. At 10 KB per session, that's a ceiling of ~200 RSVP sessions. If an attacker floods 300 session requests, the router begins rejecting new sessions. Legitimate LSP establishment during this time will fail.

**Defenses:**
- Rate limiting RSVP processing at the control plane (CoPP)
- Maximum RSVP sessions per interface or peer
- ACLs restricting RSVP (IP protocol 46) to known neighbor addresses only

#### 4. Traffic Interception via LSP Tampering

RSVP-TE does not protect the data plane. MPLS forwarding is label-based routing — anyone who can observe traffic on a link that carries MPLS labels can read and potentially modify that traffic. There is no hop-by-hop integrity or encryption in MPLS.

**If confidentiality matters:**
- Encrypt at the service layer (IPsec over L3VPN, MACsec on customer-facing interfaces)
- Use VPN service separation (different VRFs, different label stacks)
- Deploy MACsec on core links if the transport medium is physically untrusted

## 5. Monitoring Architecture

### What to Monitor

The monitoring architecture for RSVP-TE at scale has five layers, from most basic to most sophisticated:

```
Layer 1: LSP State (up/down) — "Is it working?"
  ↓
Layer 2: LSP Path (which route) — "Is it on the right path?"
  ↓
Layer 3: LSP Performance (latency, loss) — "Is it working well?"
  ↓
Layer 4: RSVP Health (sessions, state, timers) — "Is signaling healthy?"
  ↓
Layer 5: Resource Utilization (bandwidth, labels, state) — "Are we approaching limits?"
```

#### Layer 1: LSP State — The Absolute Minimum

Every monitoring system must answer this question: "Is every LSP up right now?"

**SNMP-based (traditional):**
```
# MPLS-TE-MIB
mplsTunnelTable          — per-tunnel state and configuration
mplsTunnelARHopTable     — actual recorded hops (for suboptimal path detection)
mplsTunnelCHopTable      — configured hop list
mplsTunnelOperTable      — operational status

# Key OIDs:
# mplsTunnelState (up=1)
# mplsTunnelAdminState (up=1, down=2)
# mplsTunnelPathTableIndex (identifies the LSP)
```

**Streaming telemetry (YANG, modern):**
```
# IOS-XR YANG paths
Cisco-IOS-XR-mpls-te-oper:mpls-te/global/tunnels/tunnel
Cisco-IOS-XR-mpls-te-oper:mpls-te/state/tunnel-state
Cisco-IOS-XR-mpls-oper:mpls/lsd/labels/label  # label programming

# Key fields:
# state (signaled/ready/active/down)
# operational-flags (suboptimal, in-sync, etc.)
# path-setup (type of path setup protocol)
# current-bandwidth / requested-bandwidth
```

```
# Junos YANG paths
/junos/mpls/lsp-information/lsp
/junos/rsvp/neighbor-information
/junos/rsvp/session-information
```

#### Layer 2: LSP Path Validation — Suboptimal Path Detection

An LSP can be "Up" but on the wrong path. This happens when:
- IGP reconverges and CSPF recomputes a different path
- An explicit path element goes down, causing loose-hop expansion
- Auto-bandwidth triggers re-signaling on a suboptimal path

**Detection:** Compare actual hops (ARHop) with expected hops (CHop):

```
# IOS-XR
show mpls traffic-eng tunnels name <tunnel> | include Via:
# Compare against explicit path or expected CSPF path

# Monitor actual-vs-recorded-hop divergence
# YANG: mplsTunnelARHopTable vs mplsTunnelCHopTable
```

**Alert condition:** Actual hop count differs from expected hop count by more than 1. A delta of 1 may be legitimate (transient reconvergence), but delta > 1 indicates a routing topology issue.

#### Layer 3: LSP Performance — Proactive Degradation Detection

MPLS ping gives you a binary answer (working or not). You need more than binary.

**BFD-over-MPLS for LSP health:**

```
# IOS-XR — BFD on MPLS TE tunnels
mpls traffic-eng
 tunnel <tunnel-id>
  bfd
   multiplier 3
   minimum-interval 50   ! 50ms detection → 150ms failure detection
  !
 !
!

# Junos — BFD on LSP
set protocols mpls label-switched-path <lsp-name> bfd-liveness-detection \
    minimum-interval 50
set protocols mpls label-switched-path <lsp-name> bfd-liveness-detection \
    multiplier 3
set protocols mpls label-switched-path <lsp-name> bfd-liveness-detection \
    transmit-interval minimum-interval 50
```

**Critical design decision:** BFD detects data plane failures (the label-forwarding path), not control plane failures (the RSVP signaling path). Both are needed for complete coverage:
- RSVP hello detects control plane adjacency loss
- BFD detects data plane forwarding failure
- A tunnel can have RSVP hello up but BFD down (data plane broken, control plane OK)
- This combination signals a specific failure mode: RSVP signaling works, labels/compute don't

**MPLS OAM (RFC 4379 / RFC 8029):**

BFD tells you "something is broken." MPLS OAM (LSP ping / traceroute) tells you "what is broken and where."

```
# IOS-XR — automated LSP ping
mpls traffic-eng tunnels
 tunnel-mpp
  mpls oam interval 60   ! LSP ping every 60 seconds for all tunnels
 !
!

# On-demand LSP trace
traceroute mpls traffic-eng tunnel <tunnel-id>
# This walks the label stack at each hop, identifying exactly where forwarding breaks
```

#### Layer 4: RSVP Signaling Health

Monitor the health of the RSVP signaling infrastructure itself:

```
# Key RSVP metrics:
# 1. Neighbor adjacency state (up/down/flapping)
# 2. Session count (total, per-interface, trending)
# 3. Session establishment/teardown rate
# 4. RSVP message rate (PATH, RESV, Hello, Error)
# 5. RSVP error rate (PathErr, ResvErr events per hour)

# IOS-XR streaming telemetry paths:
Cisco-IOS-XR-rsvp-oper:rsvp/neighbors
Cisco-IOS-XR-rsvp-oper:rsvp/names
Cisco-IOS-XR-rsvp-oper:rsvp/interfaces

# Junos streaming telemetry paths:
/junos/rsvp/neighbor-information
/junos/rsvp/session-information
/junos/rsvp/interface-information
```

**Red flags:**
- RSVP session count trending upward without corresponding LSP creation → zombie sessions or signaling memory leak
- RSVP hello flap on a link → IGP/L2 instability masquerading as RSVP problem
- Sudden spike in PathErr events → CSPF failure, bandwidth exhaustion, or topology change

#### Layer 5: Resource Utilization and Capacity

```
# Bandwidth utilization per LSP and per link:
show mpls traffic-eng tunnels  # per-tunnel bandwidth
show mpls traffic-eng topology # per-link reservable and residual bandwidth

# Label space utilization:
show mpls labelmanager summary  # IOS-XR
show mpls label  # Junos

# RSVP session memory:
show rsvp summary  # session count
show processes | include rsvp  # RSVP process memory
```

**Capacity thresholds:**
- **Reservable bandwidth**: Alert at 80% utilization on any link. Critical at 90%.
- **LSP count**: Alert when approaching RSVP session limits. Per-platform limits matter significantly (e.g., 9000 on 7500, 3000 on ASR9K) — consult platform-specific documentation for exact numbers.
- **Label space**: Alert when label allocation exceeds 70% of available range (typical range: 24000–1048575 per platform).
- **CPU/memory**: RSVP process exceeding baseline CPU by > 50% or growing memory over time indicates a signaling issue or potential resource leak.

## 6. Incident Response Playbooks

### Playbook 1: Single LSP Down

**Trigger:** Monitoring alert for one LSP in Down state.

```
Step 1: Confirm the tunnel state (not a stale monitoring alert)
  show mpls traffic-eng tunnels name <tunnel>

Step 2: Check the tail (most common cause: tail-end node down)
  show route <tail-loopback>
  show isis neighbor | include <tail-node>

Step 3: Check the path (is it a path computation failure or signaling failure?)
  show mpls traffic-eng tunnels name <tunnel> | include Path|ERR|State
  # If "Path Error": check PathError code
  # If "Resv Error": check ResvError code
  
Step 4: Check IGP topology (has something changed?)
  show isis database  (compare against baseline)
  # Look for new/deleted nodes, changed metrics, new TE LSAs

Step 5: Check bandwidth availability on the failed path
  show mpls traffic-eng topology
  # Look for links at or near bandwidth capacity on the expected path

Step 6: Attempt manual re-signaling
  mpls traffic-eng reoptimize force-tunnel <tunnel-id>
  # If it comes up: the path was temporarily constrained
  # If it stays down: investigate deeper (signaling failure, not resource)
```

**Resolution time SLA:** 5 minutes (if tail is reachable and path exists).

### Playbook 2: Mass LSP Failure (> 10% of tunnels down)

**Trigger:** Monitoring alert for multiple LSPs in Down state simultaneously.

```
This is NOT an LSP problem. This is a topology or signaling problem.
Think: IGP flap, node failure, RSVP process crash, or control-plane storm.

Step 1: Determine if it's a core node failure
  show isis neighbor  (are multiple neighbors down?)
  show rsvp neighbor  (are multiple RSVP neighbors lost?)
  # If one node lost many neighbors → that node is down or the link is failing
  
Step 2: Check if it's a TED corruption/TED sync issue
  show mpls traffic-eng topology  (is TED populated? does it look reasonable?)
  # If TED is empty or incomplete → IGP TE LSA flooding is broken
  
Step 3: Check RSVP process health
  show processes | include rsvp  (is the RSVP process running? what's its CPU?)
  # On IOS-XR: show processes rsvp detail
  # If RSVP process crashed → restart and monitor recovery
  
Step 4: Check for control-plane storm
  show logging  (look for RSVP or IGP flap storms)
  # Pattern: rapid adjacency up/down cycles indicate L2 flapping or routing instability
  
Step 5: If TED is healthy and RSVP is healthy → it's a bandwidth cascade
  show mpls traffic-eng topology | include "Max\|Reserved"
  # Cascading preemption: one LSP drops, freeing bandwidth → 
  # another LSP grabs it, preempting someone → cascade of preemption events
```

**Critical decision point:** If more than 50% of LSPs are down and the core is reachable:
- Do NOT restart RSVP on all routers simultaneously (this creates a signaling storm)
- Restore LSPs in priority order: highest-bandwidth, highest-impact tunnels first
- Use `admin up/down` cycling for stuck LSPs (force re-signaling from head-end)

**Resolution time SLA:** 15–30 minutes (mass failure requires topology diagnosis, not just LSP reset).

### Playbook 3: RSVP Adjacency Flap

**Trigger:** RSVP neighbor on a specific interface oscillating up/down.

```
Step 1: Determine the scope (one interface, one node, or widespread?)
  show rsvp neighbor | include <node>
  # One interface: likely physical/L2 issue or MTU
  # All interfaces to one node: node-side problem
  # Widespread: IGP instability or timer misconfiguration

Step 2: Check physical interface
  show interface <interface>  (errors, drops, flapping)
  # CRC errors → fiber degradation
  Interface up/down → L2 issue
  
Step 3: Check MTU mismatch
  show interface <interface> | include MTU
  show isis interface <interface> | include Metric|MTU  (IOS-XR)
  # RSVP hello packets are ~48 bytes. But if IGP hellos are also affected → MTU

Step 4: Check timer configuration
  show rsvp interface <interface>  (hello interval, hello misses)
  # If timer is aggressive (e.g., 1s interval) and link has minor jitter → 
  # neighbor timeout occurs intermittently
  
Step 5: Check if it's a CoPP issue
  show controllers np counters  (IOS-XR, check if RSVP packets are being rate-limited by NPU)
  # If RSVP rate limit is too low, RSVP hellos get dropped under load → neighbor flap
```

**Resolution time SLA:** 10 minutes.

### Playbook 4: Label Table Exhaustion

**Trigger:** New LSPs fail to signal; existing LSPs may become unstable.

```
Step 1: Confirm label exhaustion
  show mpls labelmanager summary  (IOS-XR)
  # Check: Dynamic labels allocated vs. total available
  # If "Free Labels" ≈ 0 or very low → label exhaustion confirmed
  
Step 2: Identify label consumers
  show mpls forwarding  (count labels by source: LDP, RSVP-TE, static, BGP-LU)
  # Which protocol is consuming the most labels?
  # LDP labels scale with routing table size (one label per IGP prefix minimum)
  # RSVP-TE labels scale with LSP count (one label per LSP per hop)
  
Step 3: Free up labels (short-term)
  # Remove unnecessary RSVP-TE tunnels
  # Aggregate LDP label distribution (label per node, not per prefix)
  # Remove static label mappings if no longer needed
  
Step 4: Long-term fix
  # Deploy LDP label allocation control (allocate labels only for required prefixes)
  # Consider label allocation reduction via LDP Downstream Unsolicited → 
  #   Downstream On Demand for specific prefixes
  # Platform upgrade if label space is fundamentally insufficient
```

**Resolution time SLA:** 10 minutes (temporary relief) / scheduled (permanent fix).

## 7. LDP/RSVP Interoperability — The Reality Check

### What Actually Happens in Production

In virtually every production MPLS network, RSVP-TE co-exists with LDP. LDP provides label distribution for the best-effort forwarding plane. RSVP-TE provides constrained-path forwarding for specific traffic flows. Understanding how they interact is not optional.

#### LDP-over-RSVP (LDP Tunneling over RSVP-TE)

This is the most common transport design: all IGP prefixes get LDP labels, and those LDP-labeled packets are tunneled over RSVP-TE tunnels. It means your customer traffic gets RSVP-TE protection without requiring per-flow RSVP signaling.

```
Packet flow:
Customer packet → PE encapsulates with LDP label → 
LDP-labeled packet enters RSVP-TE tunnel → 
RSVP-TE tunnel (with its own label) carries the LDP-labeled packet →
At tail-end, RSVP-TE label is popped → 
LDP label is used to forward to egress CE →
Customer packet delivered
```

**Operational implications:**
- If an RSVP-TE tunnel goes down, ALL LDP-labeled traffic using that tunnel is affected
- LDP does not know about RSVP-TE. If RSVP-TE tunnel fails, LDP still points at the failed tunnel
- LDP-to-RSVP-TE binding takes time to converge (typically several seconds)
- During RSVP-TE tunnel failure, LDP traffic either drops or falls back to LDP-only path (if LDP adjacency exists on an alternate path)

**Monitoring requirement:** Monitor both LDP state AND RSVP-TE state. An LDP label being "active" does not mean the transport is working — the RSVP-TE tunnel below it might be down.

```
# Check LDP-to-RSVP-TE binding
# IOS-XR
show mpls ldp discovery
show mpls forwarding | include tunnel-te  # tunnel-te = traffic forwarded over RSVP-TE tunnel

# Verify LDP traffic is actually reaching via RSVP-TE:
show mpls forwarding detail
# Look for "via TE tunnel" on LDP-labeled entries
```

**The LDP-over-RSVP convergence trap:** When an RSVP-TE tunnel fails, LDP needs to re-converge to a new transport path. The convergence time is determined by:
1. RSVP-TE failure detection (BFD: ~150ms, or RSVP hello: ~27s)
2. RSVP-TE re-signaling (make-before-break: 1–5 seconds typically)
3. LDP re-convergence to new transport (depends on LDP sync with IGP state)

The effective convergence time = RSVP-TE convergence + LDP convergence. FRR (Fast Reroute) reduces step 1 to ~50ms by pre-protecting RSVP-TE tunnels with backup paths. But LDP still needs to reconverge for full traffic recovery.

#### RSVP-TE Auto-Bandwidth and LDP Traffic

If RSVP-TE tunnels carry LDP-labeled customer traffic, and auto-bandwidth reduces the tunnel's reserved bandwidth below actual traffic volume, packets get dropped at every transit node doing admission control. This manifests as customer-impacting packet loss that is very hard to diagnose because:

1. RSVP-TE tunnel is "Up" (signaling works fine)
2. LDP labels are "Active" (LDP state is correct)
3. Customer traffic is just... disappearing

The root cause is bandwidth over-subscription: the tunnel's actual reserved bandwidth is less than the traffic trying to traverse it. Auto-bandwidth adjusts reservations, but if the adjustment interval is long (24 hours default) and a traffic burst occurs shortly after a bandwidth reduction, the tunnel is under-provisioned until the next auto-bandwidth cycle.

**Defense:** Configure overflow detection on auto-bandwidth tunnels to trigger immediate re-signal when traffic exceeds current bandwidth for N consecutive samples:

```
# IOS-XR
mpls traffic-eng
 auto-bw overflow
  minimum-overflow 2    ! minimum overflow samples to trigger
  !
!
tunnel-group 1
 auto-bw overflow
  minimum-overflow 2
 !
!
```

## 8. Fast Reroute (FRR) — Sub-50ms Protection

### Why FRR Is the Most Important Operational Feature

FRR is what separates "RSVP-TE went down for 27 seconds" from "RSVP-TE went down for 50 milliseconds." Without FRR, convergence depends on RSVP hello timeout (seconds) or BFD (sub-second). With FRR, traffic switches to a pre-computed backup path at hardware speed when BFD detects a failure.

FRR protects the data plane while RSVP-TE re-signals a new primary path. It is not a replacement for re-signaling — it is a bridge that keeps traffic flowing during the convergence window.

### FRR Modes

#### Facility Backup (RFC 4090 — Bypass Tunnels)

The Point of Local Repair (PLR) pre-signals a bypass tunnel around the protected link or node. When failure occurs, the PLR pushes the bypass tunnel label onto the label stack and forwards traffic through the bypass.

```
Normal path:   A ──[label 100]──> B ──[label 200]──> C ──> D
FRR bypass:    A ──[bypass-label][label 200]──> E ──> C ──> D
                                                ↑
                                          Bypass tunnel
```

**Link protection** protects against a single link failure (A-B link down):
```
# IOS-XR — enable link protection on primary tunnel
mpls traffic-eng
 tunnel-te 1
  fast-reroute
  !
!

# Create bypass tunnel protecting the link
interface tunnel-te 100
 mpls traffic-eng
  backup-bw global-pool unlimited
  path-option 1 explicit name BYPASS-A-TO-C
 !
!
```

**Node protection** protects against a full node failure (node B fails):
```
# IOS-XR — enable node protection
mpls traffic-eng
 tunnel-te 1
  fast-reroute protect node
  !
!

# Junos — node-link protection
set protocols mpls label-switched-path <lsp> node-link-protection
```

**Key difference:** Link protection bypass goes A→E→B→C (avoids the link but still traverses B). Node protection bypass goes A→E→C (avoids node B entirely). Node protection requires an alternate path that doesn't traverse the protected node.

#### One-to-One Backup (Detour LSPs)

Each protected LSP gets its own dedicated detour path. More state, more resource consumption, but more granular control.

```
# Junos — one-to-one detour (default FRR behavior)
set protocols mpls label-switched-path <lsp> fast-reroute
# This creates per-LSP detour paths automatically
```

**Production recommendation:** Use **facility backup** (bypass tunnels). It scales better because one bypass tunnel can protect many LSPs, whereas one-to-one backup creates a detour for every LSP. In a network with 500 LSPs through a single node, facility backup creates 1 bypass tunnel; one-to-one backup creates 500 detours.

### FRR Operational Monitoring

```
# IOS-XR — check FRR status for all tunnels
show mpls traffic-eng fast-reroute database
show mpls traffic-eng tunnels brief | include FRR

# Check which tunnels have FRR active (in protection state)
show mpls traffic-eng tunnels | include "FRR Active"

# Junos
show mpls lsp ingress extensive | match "Fast-reroute|Bypass"
show rsvp session bypass
show mpls lsp bypass
```

**Critical FRR monitoring metrics:**

| Metric | Alert Threshold | Meaning |
|--------|----------------|----------|
| Tunnels without FRR protection | Any | LSPs are unprotected — one failure = traffic loss |
| FRR activation events/hour | > 5 | Frequent protection switching indicates instability |
| Bypass tunnel utilization | > 0 for > 5 min | FRR activated but primary not recovered — investigate |
| Backup path computation failures | Any | Cannot compute bypass — topology too constrained |

### FRR Failure Modes — What Can Go Wrong

1. **No bypass computed:** The topology doesn't offer an alternate path around the protected element. This happens in ring topologies with only one alternate path that's already at capacity.

2. **Bypass bandwidth insufficient:** The bypass tunnel's reservable bandwidth is less than the sum of all protected LSPs that would simultaneously use it during a failure. Result: some LSPs get protected, some get preempted off the bypass.

3. **FRR activates but merge point unreachable:** The bypass tunnel terminates at a node that can't reach the original tail-end. This happens when node protection bypass doesn't account for downstream topology.

4. **Stale FRR state:** Primary path recovered but FRR state wasn't cleaned up. Traffic continues on bypass path (suboptimal routing, wasted bandwidth on bypass).

```
# Force reoptimization to move traffic off FRR bypass back to primary
# IOS-XR
mpls traffic-eng reoptimize

# Junos
clear mpls lsp optimize
```

### FRR + BFD Integration

FRR switches at hardware speed but needs a failure detection trigger. BFD provides that trigger:

```
# IOS-XR — BFD triggers FRR switchover
mpls traffic-eng
 tunnel-te 1
  fast-reroute
  bfd
   multiplier 3
   minimum-interval 50  ! 50ms × 3 = 150ms detection → FRR switch in ~200ms total
  !
 !
!

# Junos
set protocols mpls label-switched-path <lsp> fast-reroute
set protocols mpls label-switched-path <lsp> bfd-liveness-detection minimum-interval 50
set protocols mpls label-switched-path <lsp> bfd-liveness-detection multiplier 3
```

**The timeline:**
1. Link/node failure occurs (T=0)
2. BFD detects failure (T=150ms with 50ms interval × 3 miss)
3. FRR activates, traffic switches to bypass (T=200ms — hardware label push)
4. RSVP-TE head-end learns of failure via PathErr or RSVP hello timeout (T=9s–27s)
5. Head-end re-signals primary on new path via make-before-break (T=10s–30s)
6. Traffic moves from bypass back to new primary (T=30s+)

Customer impact: ~200ms blip instead of 10–30 seconds of outage.

## 9. Scale: What Happens When RSVP-TE Gets Big

### Per-Platform Realities

RSVP-TE scales non-linearly. Twice the LSPs costs more than twice the state because:
- Each LSP creates state on every transit node (not just head and tail)
- RSVP soft-state refresh (every 30 seconds) consumes CPU on every node
- Make-before-break temporarily doubles the state during re-signaling
- Auto-bandwidth triggers periodic re-signaling across all LSPs simultaneously

**Approximate per-platform ceilings** (these change with software releases — verify with vendor documentation):

| Platform | RSVP Sessions | LSPs | Notes |
|----------|--------------|------|-------|
| Cisco NCS 5500 | ~50,000 | ~5,000 | Distributed signaling across line cards |
| Cisco ASR 9000 | ~30,000 | ~3,000 | Centralized RSVP process on RSP |
| Juniper MX (PTX) | ~100,000 | ~10,000 | Distributed signaling via RE/fabric |
| Nokia 7750 SR | ~80,000 | ~8,000 | Distributed via CPM/line card |

**These are engineering limits, not design limits.** If you're within 20% of any of these numbers, you're in the danger zone. The actual usable capacity is approximately 50–60% of the engineering limit because you need headroom for re-signaling spikes, maintenance, and growth.
