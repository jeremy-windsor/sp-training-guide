# 13.1 — Backbone Operations & Maintenance

> **Level:** Internet Expert / IE-SP  
> **Prerequisites:** Modules 2 through 6 recommended, Module 11 helpful

---

## Overview

> Building a backbone is engineering. Keeping it stable for three years while customers, optics, software trains, power feeds, contractors, and your own change windows all try to kill it is operations. This section is about the boring machinery that separates a serious service provider from a science fair project: baselines, maintenance discipline, software lifecycle control, capacity management, incident command, and the habits that stop small faults from graduating into headlines.

**What you'll learn:**
- What “good operations” actually means in an SP backbone, beyond vague promises and dashboards with too many colors
- The minimum operational baseline every core, edge, and transport node needs before it carries production traffic
- How to structure monitoring, alerting, and escalation so the NOC sees real problems instead of confetti
- Maintenance window discipline: pre-checks, drain plans, change execution, rollback criteria, and post-checks
- Software lifecycle management: image qualification, canary rollouts, HA caveats, and when not to trust hitless-upgrade marketing
- Capacity management for links, control plane state, FIB/TCAM, route scale, and optics margins
- Configuration management, drift control, inventory hygiene, and source-of-truth requirements
- Incident handling, communication, RCA quality, and how mature operators turn outages into better runbooks
- Practical IOS-XR and Junos commands for backbone health validation and day-2 operations

**Scope note:** This is not a protocol deep-dive. Modules 2 through 11 explain how the technologies work. This section explains how to run the network that contains them without becoming the cautionary tale in someone else’s postmortem.

## 1. What Backbone Operations Actually Owns

Backbone operations owns four things simultaneously:

1. **Availability** — the network stays up and converges predictably when components fail
2. **Integrity** — forwarding, policy, timing, and management behavior remain inside the intended design envelope
3. **Recoverability** — failures are detected fast, isolated correctly, and restored with repeatable methods
4. **Change safety** — the network can evolve without every maintenance window becoming ritualized roulette

That sounds abstract until you translate it into daily responsibilities.

### The Operational Stack

A service provider backbone is not just “routers and links.” It is an operational stack:

```
Physical layer      → optics, DOM, power, cooling, cabling, patching
Link layer          → Ethernet, LAG, LOS, errors, MTU, QoS trust
Routing underlay    → IS-IS/OSPF, BFD, loopbacks, TE DB, SRGB, locators
Service overlays    → BGP, L3VPN, EVPN, SR-TE, RSVP-TE, LDP
Management plane    → AAA, TACACS/RADIUS, SSH, NTP/PTP, syslog, telemetry
Automation plane    → config generation, validation, rollback, inventory, CI
Operational plane   → alerting, runbooks, change control, ticketing, RCA
```

If any layer is weak, the layer above it lies to you.

### Operations Principles That Matter

#### 1. Every alert must have an owner

If a platform can emit an alarm but nobody knows who acts on it, that alarm is decorative. Decorative alarms are how real alarms get ignored.

#### 2. Every production node needs a known-good baseline

“Looks fine to me” is not a baseline. A baseline is measurable:
- route counts within expected bands
- control-plane adjacency count stable
- optical receive power within normal margin
- CPU, memory, FIB, label, and buffer utilization below thresholds
- management services reachable through the out-of-band path

#### 3. Every maintenance window needs a backout point

Not a vague plan. A literal checkpoint after which you stop, verify, or roll back.

#### 4. Every recurring failure should produce a permanent artifact

That artifact may be a runbook, automation guardrail, lint rule, alarm threshold, or design standard. If the same failure happens three times and you only wrote three tickets, operations learned nothing.

## 2. Minimum Day-2 Baseline for a Production Backbone

Before a router, switch, or transport node carries meaningful traffic, the operational baseline must exist. If you skip this, the network works only on good days.

### Management Plane Requirements

Every production node should have:

- **Out-of-band management** path independent of the production underlay
- **AAA** via TACACS+ or RADIUS, with documented local-breakglass fallback
- **NTP or PTP** correctly synchronized, with alarm thresholds for clock drift
- **Syslog** to redundant collectors, using severity filtering that preserves signal
- **Streaming telemetry or SNMP** to a monitoring platform with history retention
- **Config archival** to a versioned repository or backup system
- **Software inventory** with exact image, package, SMU/patch, ROMMON/loader versions
- **Hardware inventory** including optics SKU, serial, FRU population, and license state
- **Loopback and management addressing** documented in a source of truth
- **Label/SID/locator/ASN allocations** documented if MPLS or SR is in use

### Time Sync Is Not Optional

Bad time ruins RCA. It also breaks security logs, BFD correlation, streaming telemetry alignment, and any cross-device incident timeline.

**Operational requirements:**
- at least 3 authoritative time sources per domain when possible
- alert on loss of all but one source
- alert on excessive offset, not just total failure
- verify timezone handling in tooling, but keep device logging on a standard operational basis (UTC is common and sane)

### Logging Hygiene

A healthy logging design has three properties:

1. **Useful severity selection**
2. **Reliable transport**
3. **Enough retention to reconstruct a failure**

If you only keep a few minutes of logs on the box and your collector drops packets during an incident, congratulations, you built amnesia as a service.

**Recommended logging practice:**
- forward to at least two collectors
- preserve local buffer for short-window triage
- log config commits, interface state transitions, protocol adjacency changes, process restarts, HA switchover events, power/thermal events, and authentication failures
- filter or rate-limit repetitive low-value messages that can drown higher-severity events

### Monitoring Baseline Checklist

A backbone node is not operationally ready until these are visible centrally:

| Domain | Must Monitor | Why |
|---|---|---|
| Hardware | RE/RP health, line card state, fan, PSU, temperature | Hardware faults often appear as “routing issue” first |
| Interfaces | up/down, errors, discards, utilization, flaps, MTU mismatches | Most outages still start at the edge of a fiber or port |
| Routing | IGP adjacencies, BGP session state, route counts, convergence events | Core control-plane health |
| MPLS/SR | label state, LSP/SR policy state, TE/SID resource use | Transport overlays fail quietly when ignored |
| Management | AAA reachability, NTP sync, telemetry exporter health | Blind networks die louder |
| Capacity | CPU, memory, FIB/TCAM/label space, optics margin, queue drops | Preventive maintenance beats emergency expansion |

## 3. Backbone Health Model and Golden Signals

You do not need infinite dashboards. You need the right signals, layered correctly.

### Layer 1: Physical Health

This is where the body count starts.

Track:
- optics receive/transmit power and drift over time
- CRC, giants, runts, symbol errors, PCS/FEC counters
- LAG member consistency
- PSU/fan status
- temperature excursions
- line-card resets or fabric path faults

**Rule:** A backbone link with zero hard-down events can still be unhealthy. Optical margin erosion, intermittent CRC bursts, and FEC correction spikes are pre-failure indicators. Mature operators alert on degradation trend, not just loss-of-signal.

### Layer 2: Forwarding Health

Track:
- per-interface discards and queue drops
- adjacency programming failures
- FIB install failures
- label/SID programming issues
- ECMP or hash polarization symptoms
- BFD state on critical paths

A route in the RIB is not proof of forwarding. Hardware programming failures are the kind of thing that makes dashboards say green while customers say otherwise.

### Layer 3: Control Plane Health

Track:
- IGP adjacency count and flap rate
- BGP established count, flap rate, prefixes accepted/advertised
- LDP/RSVP/SR policy state if deployed
- route churn rate
- SPF frequency, BGP update spikes, RIB failures
- process restarts, process memory growth, high sustained RE/RP CPU

**Threshold principle:** Alert on sustained abnormality, not every blip. A single SPF is life. Fifty in five minutes is a crime scene.

### Layer 4: Service Health

Track:
- VPN route counts by service class
- tunnel or policy utilization for engineered paths
- packet loss / latency / jitter on critical classes
- synthetic probes between major POPs and service edges
- customer-facing traffic asymmetry after failover events

### Layer 5: Operational Health

Track:
- telemetry gaps
- collector backlog
- config backup failures
- inventory drift
- missing documentation on new links, peers, or devices
- alert suppression that outlives the maintenance window it was meant for

If the network is healthy but your observability plane is blind, you are one bug away from interpretive dance.

### Suggested Alert Threshold Bands

These are operational starting points, not laws of physics:

| Metric | Warning | Critical | Notes |
|---|---|---|---|
| Backbone link utilization | 60–70% sustained | 80%+ sustained | Leave headroom for failures and maintenance |
| RP/RE CPU | >70% sustained | >85% sustained | Short spikes are normal during churn |
| Memory | >75% sustained | >90% sustained | Watch trend, not only current point |
| Optics margin | vendor/platform dependent | near minimum Rx threshold | Trend toward failure matters more than one sample |
| Interface errors | non-zero recurring | increasing burst trend | Persistent low-rate errors are still real |
| Route scale | >80% of tested capacity | >90% | Include FIB and control-plane limits |
| Label/SID space | >70% | >85% | Especially relevant for SR and TE-heavy backbones |

## 4. NOC, Escalation, and Runbook Design

An SP backbone cannot depend on tribal knowledge plus one engineer who answers texts at church.

### Separation of Duties

At minimum, define:
- **NOC** — detects, triages, runs first-line validation, executes approved low-risk playbooks
- **Backbone engineering** — owns protocol design, deeper fault isolation, non-routine maintenance, and standards
- **Transport/optical** — owns layer-1 fault isolation and vendor/escalation on physical impairments
- **Systems/automation** — owns tooling, collectors, config pipelines, and observability infrastructure
- **Incident commander** — coordinates communications, timelines, and decision gates during major incidents

One human may wear several hats in a small team. The roles still need to exist.

### What a Good Runbook Contains

A real runbook answers five things quickly:

1. **How do I detect this failure?**
2. **What are the first three checks?**
3. **What is safe to do immediately?**
4. **What is explicitly unsafe without escalation?**
5. **What evidence do I collect before the state changes?**

### Runbook Anti-Patterns

Bad runbooks usually do one of these:
- assume the reader already knows the topology
- omit rollback criteria
- give commands but not expected outputs
- instruct global actions before local isolation
- confuse escalation with progress

If the runbook says “check all routing” it is not a runbook. It is a cry for help.

## 5. Change Management and Maintenance Windows

Maintenance quality is one of the clearest maturity indicators in an SP shop.

### The Maintenance Sequence

Every non-trivial backbone change should follow this order:

1. **Pre-check** — establish current healthy state
2. **Blast-radius review** — know what can break and who notices first
3. **Traffic-drain or protection validation** — reduce exposure before touching the box or path
4. **Change execution** — one bounded action at a time
5. **Immediate verification** — confirm the expected outcome before proceeding
6. **Post-check** — compare against baseline, not against vibes
7. **Rollback or close** — based on explicit criteria

### Pre-Check Data to Capture

Before touching a backbone node or link, collect:

- hardware alarms and environmental state
- interface state, errors, and utilization
- IGP adjacency summary
- BGP summary and route counts
- MPLS/LDP/RSVP/SR summaries if relevant
- current software version and uptime
- active maintenance suppressions or ticket correlations
- recent log buffer focused on the target interfaces/processes

### Example Operational Validation Commands

**IOS-XR**
```cisco
show alarms brief
show platform
show environment all
show interfaces brief
show interfaces counters rates
show interfaces counters errors
show isis neighbors summary
show bgp summary
show route summary
show mpls forwarding summary
show logging last 100
```

**Junos**
```junos
show system alarms
show chassis alarms
show chassis routing-engine
show chassis fpc pic-status
show interfaces terse
show interfaces extensive | match "Physical interface|errors|drops|flapped"
show isis adjacency
show bgp summary
show route summary
show log messages | last 100
```

### Rollback Criteria Must Be Explicit

Examples of valid rollback triggers:
- unexpected adjacency loss outside the maintenance scope
- forwarding loss for protected traffic after protection should have engaged
- route count or prefix acceptance deviation beyond pre-agreed tolerance
- control-plane instability lasting longer than the change plan allows
- inability to restore out-of-band or management-plane access

Examples of invalid rollback logic:
- “if it looks weird”
- “if customers complain a lot”
- “if we feel nervous”

### Draining Traffic Before Risky Work

For disruptive work, validate one of these before proceeding:
- IGP metric increase or overload/maintenance signal has shifted traffic away
- SR-TE / RSVP-TE / LSP protection is active and carrying load as expected
- LAG member removal leaves sufficient capacity
- BGP maintenance policy drains edge traffic without destabilizing route policy

Do not assume redundancy. Prove it.

### Post-Check Discipline

A maintenance window is not done when the config commits. It is done when:
- pre-check and post-check state match where they should
- intentional deviations are documented
- alarms are reviewed, not merely suppressed
- traffic levels normalize
- protection or backup state is restored if temporarily changed

## 6. Software Lifecycle and Upgrade Strategy

Most large outages blamed on “software” were really failures of software lifecycle discipline.

### Principles for Backbone Software Management

1. **Standardize on approved trains** per platform role
2. **Qualify images in a lab or canary ring** before broad deployment
3. **Track bugs against your feature set**, not just the base release notes
4. **Limit simultaneous variables** during upgrades, meaning image change alone unless absolutely necessary
5. **Never trust the word hitless until you’ve tested your exact hardware, feature set, and topology**

Marketing says ISSU. Reality says “it depends,” which is networking’s least romantic phrase.

### Upgrade Rings

A sane rollout model:

1. **Lab / spare node** — validate image boot, config parse, feature presence, management-plane compatibility
2. **Canary POP or low-risk pair** — real traffic, low blast radius
3. **Representative production cohort** — includes your common line cards and service mix
4. **Broad deployment** — after enough soak time to catch slow failures

### What to Validate Before Upgrading

- target release supports all in-use features, scale, and hardware
- downgrade path exists and is tested/documented
- patch/SMU requirements are known
- boot variables and package consistency are clean
- automation tooling supports the image syntax/model version
- line-card firmware and ROMMON implications are understood
- maintenance duration includes realistic reboot and control-plane reconvergence time

### High-Availability Caveats

Dual-RP/dual-RE systems reduce risk. They do not repeal it.

Features commonly marketed as non-disruptive or graceful include:
- **GR/NSR** for routing protocol continuity
- **GRES/NSR/NSSU** on Junos for RE and switching continuity in supported cases
- **ISSU/eXR upgrade workflows** on IOS-XR in supported hardware/software combinations

Operationally, the correct stance is:
- verify feature support on your exact platform, release, and deployed features
- assume some control-plane churn unless proven otherwise
- assume some traffic impact is possible when line-card, fabric, or optics firmware changes are involved
- validate post-upgrade forwarding, not just session re-establishment

### Post-Upgrade Failure Patterns to Watch

The dangerous bugs are often not immediate. Watch for:
- memory growth over hours or days
- optics or PHY behavior changes on specific modules
- protocol flap rate increase under churn
- telemetry schema or path changes that silently break monitoring
- route-policy evaluation differences after parser or RPL/policy engine changes
- line-card inconsistency after partial reload or fabric reintegration

## 7. Configuration Management and Drift Control

A backbone without config discipline slowly turns into folklore.

### Required Source-of-Truth Domains

At minimum, maintain authoritative records for:
- device inventory and ownership
- hostname, loopback, management, ASN, router ID
- interface-to-circuit mapping
- POP/site/rack/power context
- optics inventory and circuit IDs
- IGP metrics and area/level membership
- BGP peers and policy intent
- MPLS/SR allocations: labels, SRGBs, locators, flex-algos, colors, BSIDs if applicable
- software image and patch state

If those live partly in chat, partly in a spreadsheet, partly in three engineers’ heads, that is not a source of truth. That is a séance.

### Drift Control Model

Config drift comes in two flavors:

1. **Authorized but undocumented drift** — the classic “hotfix at 3am”
2. **Unauthorized drift** — manual changes bypassing review or automation

Both must be detectable.

**Best practice:**
- archive all running configs after every commit/change window
- diff against intended state or last-approved baseline
- alert on changes outside approved windows if your environment supports it
- track commit/user/comment metadata where the platform exposes it

### Commit Hygiene

Every significant config change should include:
- change ticket or maintenance reference
- intent in human language
- expected outcome
- rollback note if applicable

Good commit comments save postmortems. Bad ones produce archaeology.

### Templates, Automation, and Guardrails

Automation should prevent known-bad patterns, for example:
- duplicate router IDs
- inconsistent BFD timers on paired links
- MTU mismatch across core circuits
- missing logging/NTP/AAA/telemetry stanzas on new nodes
- route-policy object references that do not exist
- overlapping SRv6 locators or TE identifiers

The purpose of automation is not to replace engineering judgment. It is to prevent unforced errors so engineering judgment can focus on the weird stuff.

## 8. Capacity Management

Capacity planning in a backbone is not just “watch 95th percentile bandwidth.” That’s how you wake up to a failover event turning 62% utilization into a saturated core.

### Capacity Domains to Track

#### Link Capacity

Track:
- sustained utilization bands
- peak utilization during known busy windows
- failover-case utilization (N-1, and sometimes N-2 for critical corridors)
- microburst behavior if the service mix is bursty
- LAG member imbalance and hash efficiency

**Design rule:** Backbone links should have enough headroom to survive realistic failure scenarios, not just average Tuesday.

#### Control-Plane Scale

Track:
- IPv4/IPv6 RIB and FIB counts
- BGP path count and update rate
- label table usage
- SR policy or tunnel count
- BFD session count
- adjacency count and TE database size if relevant

A platform can look idle on CPU and still be one route leak away from collapse because a finite table is almost full.

#### Hardware Lifecycle Capacity

Track:
- free slots, optics reserves, spare FRUs, lead times
- line-card and optics end-of-sale / end-of-support milestones
- transponder muxponder shelf capacity if optical transport is in scope
- power and cooling headroom in the POP, not just router chassis headroom

#### Timing and Telemetry Capacity

Yes, even observability has capacity limits:
- collector ingest rates
- telemetry subscription fan-out
- flow export volume
- syslog event storms during incidents

When the monitoring stack melts during a failure, you discover too late that you only instrumented the happy path.

### Capacity Review Cadence

A mature backbone team runs at least:
- **daily** anomaly review for critical utilization and alarms
- **weekly** operational review of hotspots, recurring errors, and churn
- **monthly** capacity and trend review
- **quarterly** lifecycle review: hardware, optics, software, support contracts, spares

## 9. Incident Handling and Communications

The first victim in an outage is usually precision of language.

### Incident Priorities

In order:
1. stabilize the network
2. preserve evidence
3. communicate clearly
4. restore normal state
5. understand why it happened
6. make it harder to repeat

### Major Incident Structure

For significant backbone incidents, designate:
- **incident commander** — owns pace, priorities, decision gates
- **technical lead** — owns diagnosis and recovery actions
- **scribe** — captures timeline, evidence, hypotheses, and decisions
- **communications owner** — customer/internal updates

One person can perform multiple roles in a small team, but all roles still need to be consciously covered.

### The First Five Minutes

Do these before random heroics:
- declare the incident and severity
- identify affected geography/services/classes
- freeze non-essential concurrent changes
- capture volatile evidence: logs, adjacency state, alarms, optics, CPU, route counts
- identify whether the problem is physical, forwarding, control-plane, service-plane, or management-plane first

### Evidence to Preserve

Before the state disappears, grab:
- log excerpts around failure start
- interface and optics counters
- adjacency summaries and flap indicators
- control-plane event counters
- route summaries and anomalies
- BFD/LSP/SR policy state if transport engineering is involved
- config diffs if any changes were in flight

### Communication Rules

Good outage communication:
- states what is known
- states what is being tested
- avoids pretending hypotheses are facts
- includes next update time
- identifies customer impact clearly

Bad outage communication:
- “investigating issue” repeated like a haunted smoke alarm
- excessive confidence early in the event
- mixing layer-1 symptoms, routing symptoms, and guessed causes as if they are the same thing

## 10. Root Cause Analysis and Continuous Improvement

If RCA becomes blame theater, engineers stop telling the truth. Then you get comforting fiction instead of useful correction.

### What a Good RCA Produces

A quality RCA should identify:
- **trigger** — what changed or failed first
- **contributing factors** — why the trigger had wider impact than it should have
- **detection gap** — why it was not detected earlier or classified correctly
- **response gap** — what slowed restoration
- **prevention actions** — standards, tooling, training, architecture, or process changes

### Bad RCA Patterns

- “human error” as the final answer
- “software bug” with no explanation of missing blast-radius controls
- no timeline reconstruction
- no discussion of why monitoring or maintenance gates failed
- action items that say “be more careful”

“Be more careful” is not a control. It is a wish.

### Turning Outages into Guardrails

The best prevention action is usually one of these:
- add a pre-check or post-check to the Method of Procedure (MOP)
- add a lint rule or automation validation
- change default alert thresholds or correlation logic
- reduce failure domain size
- document a previously tribal procedure
- redesign the topology or policy so one component cannot create disproportionate impact

## 11. Preventive Maintenance and Operational Hygiene

Most catastrophic outages are the final exam of a long series of ignored warning shots.

### Recurring Hygiene Tasks

#### Daily
- review critical alarms and unresolved warnings
- review interface error deltas on critical links
- confirm telemetry/syslog/config backup health
- review route and session anomalies on core and edge roles

#### Weekly
- inspect flapping links or protocols, even if auto-recovered
- review optics trending and FEC correction outliers
- verify recent changes were documented and archived correctly
- audit suppressed alerts and maintenance windows that should have expired

#### Monthly
- capacity trend review
- software defect and patch review against deployed trains
- config drift audit
- spare inventory check for optics, FRUs, and console/OOB access paths
- test a few backup/restore and access assumptions, not just production forwarding

#### Quarterly
- out-of-band management failover validation
- AAA fallback verification
- escalation tree review
- major runbook review and refresh
- hardware lifecycle and contract review

### The “Recovered by Itself” Trap

A flapped adjacency that came back is still evidence.
An interface that errored for ten minutes and then stopped is still evidence.
An optics lane that dipped and recovered is still evidence.

Backbones often warn you in low-volume, polite ways before they fail rudely.

## 13. Common Failure Patterns

### 1. Partial Optics Failure Masquerading as Routing Instability

**Symptoms:** intermittent BFD drops, IGP flap, CRC bursts, traffic loss under load only  
**Likely cause:** degraded optic, dirty fiber, marginal power, bad patch lead  
**Fix:** validate DOM trend, clean/replace optics and patching, compare both directions, involve transport if the plant is suspect

### 2. Maintenance Window Finished, Protection State Never Restored

**Symptoms:** network is up, but running hot or on suboptimal paths for hours/days  
**Likely cause:** temporary metric/policy/tunnel changes left in place  
**Fix:** explicit post-check item for protection-state normalization; alert on prolonged maintenance state

### 3. Slow-Burn Resource Exhaustion

**Symptoms:** no obvious outage until a churn event, then routing/FIB instability  
**Likely cause:** route scale, label exhaustion, RE memory growth, telemetry process leak  
**Fix:** trend finite resources, define warning bands, treat steady growth as a ticket before it becomes an incident

### 4. Config Drift Breaks the Next Change, Not the Current One

**Symptoms:** new maintenance fails unexpectedly on one node only  
**Likely cause:** undocumented hotfix or stale exception  
**Fix:** config archival, drift audit, enforce change comments and post-incident normalization

### 5. Monitoring Blindness During Incident

**Symptoms:** collectors or telemetry exporters fail exactly when needed most  
**Likely cause:** insufficient observability capacity, single collector, untested failure mode  
**Fix:** redundant collectors, backpressure planning, rate limits, synthetic health checks for the monitoring stack itself

## 14. What Good Looks Like

A backbone operations team is healthy when:
- maintenance windows are boring
- route, optics, and platform baselines are known, not guessed
- new engineers can run first-line triage from documented playbooks
- alert volume is low enough that critical alarms feel unusual
- outages produce durable controls, not just emotionally satisfying blame
- software rollouts are staged and reversible
- the source of truth is accurate enough to support automation without prayer

That is the job. Not memorizing commands, not collecting cert logos, not building the world’s most expensive Christmas tree dashboard. Just making a very large, very complicated network behave predictably under stress.

## Operational Checklist

### Before Declaring a Node Production-Ready
- [ ] OOB reachable
- [ ] AAA and local fallback validated
- [ ] Time sync validated
- [ ] Syslog and telemetry verified centrally
- [ ] Config archival working
- [ ] Hardware/software inventory recorded
- [ ] Routing and service baselines captured
- [ ] Runbooks and ownership defined

### Before a Backbone Maintenance Window
- [ ] Pre-check captured
- [ ] Impacted services and blast radius reviewed
- [ ] Drain / protection behavior validated
- [ ] Rollback criteria documented
- [ ] Communications path and update cadence defined
- [ ] Post-check commands prepared in advance

### After a Backbone Incident
- [ ] Timeline reconstructed
- [ ] Volatile evidence preserved
- [ ] Trigger and contributing factors identified
- [ ] Detection and response gaps documented
- [ ] Durable prevention actions assigned and tracked
