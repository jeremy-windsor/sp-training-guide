## Overview

> SRv6 is the most powerful forwarding plane innovation in service provider networking in two decades. It is also, by design, the most porous. Understanding why takes about five minutes. Fixing it takes a lot longer. This section covers the actual security model of SRv6 — not the aspirational one in marketing decks, but the one that exists on your backbone at 2am.

**What you'll learn:**
- Why SRv6 has no unique ethertype and why that matters for every firewall in your network
- The SRH trust boundary model from RFC 8754 and what "untrusted source" means operationally
- How SID spoofing attacks work and how to think about containment
- Infrastructure ACL design for SRv6 at domain edges
- How vendors differ in their SRH handling and filtering capabilities
- SRv6 vs SR-MPLS: an honest security comparison
- Recommended security architecture for production SRv6 backbones

## The Fundamental Problem

This needs to be stated clearly before anything else, because it changes how you think about every security decision in an SRv6 deployment:

**SRv6 is IPv6. There is no distinguishing ethertype.**

SR-MPLS uses Ethertype `0x8847`. Every firewall, ACL engine, and IDS that understands MPLS knows where the MPLS traffic starts. You can filter on the ethertype. You can deny MPLS forwarding from untrusted sources at the edge. The label space is local — labels are only meaningful within the MPLS domain and carry no forwarding semantics outside it.

SRv6 uses Ethertype `0x86DD` — standard IPv6. The Segment Routing Header is Routing Header Type 4 (RH4), an extension header nested inside a normal IPv6 packet. A firewall that inspects IPv6 but does not specifically look for RH4 extension headers sees SRv6 traffic as ordinary IPv6. It applies IPv6 ACL rules. It passes it.

This is not a vendor implementation bug. This is the architecture. SRv6 was designed to work over any IPv6-capable network, including networks whose transit devices have no idea that SRv6 exists. RFC 8754 §3.2 defines this explicitly: "A transit node is not required to be capable of processing a segment or SRH." It is a defined design characteristic that SRv6 can traverse unmodified IPv6 infrastructure.

The security implication is the mirror image of that feature: **if you have IPv6 reachability to an SRv6-capable node, you can potentially inject a crafted SRH and influence how that node forwards traffic.**

This is the threat model. Everything else in this section is a response to it.

## Single-Segment SRv6 — The Attack Surface You Can't Filter with RH4

Before we get into packet anatomy, there's a fact that most SRv6 security discussions miss and that undermines half the filtering advice you'll find on the internet:

**SRv6 does not require an SRH.**

RFC 8754 §4.1 explicitly allows a single-segment SR Policy to omit the SRH entirely. If only one SID is needed — the headend encapsulates with the SID in the IPv6 Destination Address, no Routing Header, no extension header, no RH Type 4 to match on. The packet is indistinguishable from ordinary IPv6 unless you know the destination is a SID.

This has profound security implications:

- **RH Type 4 filters are necessary but not sufficient.** ACL rules that match `routing-type 4` or `extension-header routing-header` catch multi-segment SRH traffic but are invisible to single-segment traffic. If your entire SRv6 security model is "block RH4 at the edge," an attacker using a single SID walks right through.
- **Destination-based filtering is the universal control.** Dropping packets with DA in your SID block (`deny ipv6 any fc00::/32`) catches both SRH-bearing and no-SRH traffic. This is why RFC 8754 §5.1 prioritizes destination-based filtering — it doesn't depend on extension header inspection.
- **Attack surface includes all SIDs, not just multi-hop ones.** A single-segment packet targeting `End.DT4`, `End.DX4`, `End.B6.Encaps`, or any other SID function is just as dangerous as a multi-hop SRH packet — and harder to detect.

**What this means for your security architecture:**

| Filter Type | Catches SRH Traffic | Catches No-SRH Traffic | Coverage |
|------------|--------------------|-----------------------|----------|
| `routing-type 4` match | ✅ Yes | ❌ No | Partial |
| Destination-based SID block filter | ✅ Yes | ✅ Yes | **Complete** |
| GUE/UDP port filter | ✅ (encapsulated) | ✅ (encapsulated) | Encap-specific |

The destination-based SID block filter is the only control that covers all SRv6 traffic regardless of encapsulation or SRH presence. Everything else is defense-in-depth — valuable, but not sufficient alone.

## SRv6 Packet Anatomy — Security Perspective

Before discussing defenses, you need to understand exactly what an SRv6 packet looks like, because the attack surface lives in specific header fields.

```
┌────────────────────────────────────────────────────────┐
│ IPv6 Base Header (40 bytes)                            │
│   Version=6  TC  Flow Label                            │
│   Payload Length  Next Header=43  Hop Limit            │
│   Source Address: (outer IPv6 source — the PE)         │
│   Destination Address: ACTIVE SID (current segment)    │
└────────────────────────────────────────────────────────┘
│ Segment Routing Header — RH Type 4 (RFC 8754)          │
│   Next Header       — protocol of payload              │
│   Hdr Ext Len       — SRH length in 8-octet units,      │
│                        excluding the first 8 octets     │
│   Routing Type = 4  — identifies this as SRH           │
│   Segments Left     — decrements at each SID           │
│   Last Entry        — index of last element in list    │
│   Flags (8 bits)    — currently all reserved           │
│   Tag (16 bits)     — packet classification (optional) │
│   Segment List[0]   — LAST segment (final destination) │  ← wire order: [0] at top
│   ...                                                  │
│   Segment List[n]   — FIRST segment (in IPv6 DA now)   │  ← Segments Left starts at n
│   Optional TLVs     — HMAC TLV, padding, etc.          │
└────────────────────────────────────────────────────────┘
│ Inner Payload (IPv6, IPv4, Ethernet, etc.)              │
└────────────────────────────────────────────────────────┘
```

**Key fields for security analysis:**

**Destination Address** — This is the active SID. At each node, the IPv6 DA is a SID local to that node. After processing, the node decrements Segments Left and sets the DA to the next SID in the list. An attacker who can write the Segment List controls the forwarding path.

**Segment List** — The ordered list of SIDs encoding the full path. Per RFC 8754 §2: "The Segment List is encoded starting from the last segment of the SR Policy." That means Segment List[0] is the **final destination** (last segment), and Segment List[n] is the **first hop** (active segment, already loaded into the IPv6 DA). Processing advances from index n downward to 0. The list is written by the headend; endpoints only advance the pointer.

**Segments Left** — A pointer into the Segment List. When Segments Left=0, the packet is at the final segment endpoint and delivered to the inner payload. Transit nodes are not expected to inspect or modify the SRH per RFC 8754 §3.2, and unauthorized modification of this field will generally corrupt intended forwarding or fail HMAC validation if HMAC is enforced. However, a compromised transit device *can* alter Segments Left or the DA to create misroutes, path perturbation, or denial of service — which is why boundary filtering (preventing injection) is more important than relying on SRH immutability in transit.

**HMAC TLV** — Optional extension defined in RFC 8754 §2.1.2. Provides cryptographic integrity over the SRH. The headend signs the SRH with an HMAC key shared with segment endpoints. HMAC verification is **optional and policy-driven** — operators configure where verification is required; it is not universally mandatory. When deployed and verified, any modification of the SRH in transit (adding, removing, or changing segments) invalidates the HMAC under the RFC-defined computation model. If the endpoint does not verify (or the HMAC TLV is absent), there is no integrity protection.

## The Trust Boundary Model — RFC 8754

RFC 8754 §5.1 ("Securing the SR Domain") is the key normative reference for SRv6 security. The section establishes that securing the SR domain requires two complementary controls: first, boundary nodes must drop inbound packets with a destination address belonging to a SID within the SR domain (destination-based boundary filtering); second, each interior node must drop packets destined to one of its local SIDs when the source address is not within the SR domain (per-node source validation). Both controls are required — neither alone is sufficient.

This is an important nuance: the RFC's **primary** mechanism is **destination-based filtering** at the domain boundary — drop traffic destined to your SID block from outside your domain. The source-address check is a **per-node** second layer that complements the boundary filter. Operationally, both matter:

**Domain boundary:** Filter on destination address — drop packets with DA in your SRv6 locator block that arrive from external interfaces. This is the primary control.

**Per-node:** Each SRv6-capable PE validates that packets destined to its local SIDs come from authorized sources. This catches attacks that bypass the boundary (compromised internal hosts, rogue devices).

The RFC establishes two categories of SRv6 traffic:

**Trusted domain traffic** — SRv6 packets sourced from within your administrative domain. You've assigned the SID block. You control the SRH-capable nodes. Traffic arriving from within the domain and destined to a domain SID is expected and legitimate.

**Untrusted traffic** — Traffic arriving from outside your domain and destined to your SID block. These MUST be dropped at domain edges per RFC 8754 §5.1.

**What "untrusted" means operationally:**

The RFC says drop it. Operationally, you have to decide where "the edge" is. Four models in practice:

| Model | Where to Filter | Pros | Cons |
|-------|----------------|------|------|
| **Customer edge** | CE-facing ports | Maximum protection | Most ACL entries to maintain |
| **Internet edge** | Upstream/peering ports | Protects from external attack | Internal abuse still possible |
| **Domain edge** | SRv6-domain boundary | Matches RFC intent | Must define domain clearly |
| **Nothing** | (no filtering) | Easy | Exposed to all injection attacks |

The right answer is customer edge AND internet edge. Both. Defense in depth.

**The gap between RFC and reality:**

RFC 8754 tells you what to do. It does not tell you:
- What ACL syntax to use on your hardware (it varies by vendor and ASIC generation)
- Whether your hardware can inspect IPv6 extension headers at line rate (it often cannot)
- Whether your firewall's IPv6 inspection engine understands RH Type 4 (many don't)
- What to do about IPv6 transit peers who originate legitimate SRv6 traffic

**Additional normative reference:** RFC 9288 ("Recommendations on Filtering of IPv6 Packets Containing IPv6 Extension Headers at Transit Routers") provides operational guidance on filtering IPv6 extension headers, including SRH (RH Type 4). It recommends that transit routers drop packets with unknown or unwanted extension header types. This document is a useful complement to RFC 8754 §5.1 — where 8754 says "filter SRv6 at domain edges," 9288 says "here's how to think about extension header filtering in general."

Every SP deploying SRv6 has to answer these questions in their specific environment. The RFC gives you the policy. Your hardware gives you the capability. The gap between them is your risk exposure.

## Attack Scenarios

### Scenario 1: SRH Injection — Source Routing Through Backbone Nodes

**Setup:**  
An attacker has IPv6 connectivity to your network (customer port, peering, compromised host inside). They craft a packet with a handwritten SRH containing SIDs of your internal backbone nodes. Their goal: route traffic through nodes they shouldn't reach, observe or manipulate traffic at those nodes, or establish a forwarding path that bypasses security controls.

**Attack packet:**
```
Outer IPv6:
  Source: 2001:db8:atk::/48   (attacker-controlled address)
  Destination: fc00:0:pe3:e001::  (SID at PE3 — attacker wants to hit this node first)
  Next Header: 43 (Routing Header)

SRH:
  Routing Type: 4
  Segments Left: 2
  Segment List:
    [0] fc00:0:pe7:dt4::100:1  (final delivery — END.DT4 at PE7, table 100)
    [1] fc00:0:pe5:x001::      (END.X at PE5, steer toward different egress)
    [2] fc00:0:pe3:e001::      (END at PE3 — already in DA)
```

**What happens if you're not filtering:**  
PE3 receives this packet. The SID `fc00:0:pe3:e001::` is in PE3's SID table. PE3 processes it — decrements Segments Left, sets DA to `fc00:0:pe5:x001::`, and forwards toward PE5. PE5 processes `END.X`, steers via the specified adjacency. PE7 processes `END.DT4`, decapsulates, and delivers to VRF table 100.

The attacker has just routed through three backbone PEs, through a VPN table they shouldn't have access to, by writing those SIDs into an SRH. Without filtering, your SID space is reachable from anywhere with IPv6 connectivity.

**What should stop this:**  
Per RFC 8754 §5.1 Level 1: domain boundary ACL drops any packet with DA in your SRv6 SID block (`fc00::/32` in this example) arriving from external interfaces. The attacker's packet has DA `fc00:0:pe3:e001::` — that's in your SID block, arriving from a customer port. Drop. Level 2 (per-node): PE3 itself drops traffic to its local SIDs from sources outside the SR domain.

---

### Scenario 2: SID Enumeration and Topology Mapping

**Attack:** Even without injecting SRH, an attacker with IPv6 connectivity can probe your SID allocation. SIDs are advertised via IS-IS/OSPFv3 extensions — they're reachable IPv6 prefixes. An attacker can:
1. Passively receive routing updates if they have iBGP/IGP access (route server, looking glass)
2. Probe the SID block iteratively (fc00:0:X:func:: for all X) and observe ICMP responses
3. Map your backbone topology: which nodes exist, how many SID types per node, what functions are exposed

This is reconnaissance. **If your SID plan embeds meaning in the SID value** (sequential numbering, node IDs in the prefix, table IDs in the function bits), topology and service role leakage becomes much easier. The SID block structure may reveal:
- Node count (how many /48s under your SRv6 block are active)
- Function count per node (how many END variants each node has)
- VPN tables (END.DT4/DT6 functions reveal VRF table IDs)

**Mitigation:**  
This is harder to fully prevent because the SIDs must be routable. Best practice:
- Don't expose SID blocks in public routing (BGP communities to control export)
- Use opaque or randomized function assignments (don't use sequential fc00:0:1:1::, fc00:0:1:2::, etc.)
- Implement RTBH (Remote Triggered Blackhole) for probe sources
- Monitor for scanning patterns: large volumes of ICMP toward SID block addresses

### Scenario 3: SRH-Based Firewalling Bypass

**Setup:**  
A firewall sits in the path between two network segments. It inspects IPv6 traffic and enforces a policy: traffic from Zone A to Zone B must use explicit permitted paths. An attacker in Zone A crafts an SRH that routes traffic around the firewall — through another SRv6 node that connects A to B without the firewall in the path.

```
Normal path: Zone A host → Firewall → Zone B host  (BLOCKED by FW policy)
SRH path:    Zone A host → SRH[PE4, PE5] → Zone B host  (Firewall never sees it)
```

**Why this works (or used to work):**  
Firewalls that don't inspect the SRH assume the IPv6 DA is the final destination. They see a packet from Zone A to `fc00:0:pe4:e001::` — which might be an "allow" entry (PE4 is inside the network). The packet routes to PE4, which processes the SRH and steers to PE5, which delivers to Zone B. The firewall never evaluated the actual delivery destination.

**Why this is worse than it sounds:**  
End-to-end SRv6 paths can bypass not just firewalls, but any middlebox — IDS/IPS, DLP, traffic inspection, lawful intercept — if those middleboxes don't understand SRH semantics. If your security architecture assumes "all traffic from A to B passes through the inspection point," SRv6 can violate that assumption.

**Mitigation:**  
1. Firewalls in SRv6 paths must understand SRH — they must chase the full segment list to determine actual delivery destination, not just the IPv6 DA
2. If your firewall cannot inspect SRH, it should block RH Type 4 at the segment boundary (fail-closed, not fail-open)
3. Audit your traffic inspection assumptions: if any inspection point assumes path coverage, verify that SRv6 paths cannot bypass it

### Scenario 4: Transit Node Exposure — The "Invisible" Forwarding Problem

This scenario is unique to SRv6 and has no direct SR-MPLS analog.

**RFC 8754 §3.2 (Transit Node)** explicitly describes this as a design characteristic: SRv6 can traverse nodes that are IPv6-capable but SRv6-unaware. Those nodes see normal IPv6 traffic. They forward it based on the Destination Address (the active SID). They do not process the SRH. Segments Left never decrements at these nodes.

**The security implication:**  
A "transparent transit" node:
- Has no idea it's in an SRv6 path
- Applies no SRv6-specific filtering (it doesn't know any is needed)
- Cannot log SRH contents (it doesn't know they exist)
- Cannot enforce SID validity (it never looks at the SID)

If an attacker routes SRv6 traffic through a transit device that happens to connect two otherwise-isolated segments, that device has no mechanism to prevent it. Its IPv6 forwarding table says "send this toward the DA" — and that's what it does.

**Practical impact:**  
This matters most in network designs where IPv6 routing and SRv6 routing are not identical. If you have a path that exists in IPv6 (because you're dual-stack for operations) but you never intended SRv6 to use it, SRv6 will use it if a SID is reachable via that path. Your SRv6 traffic engineering topology is a subset of your IPv6 forwarding topology. Misaligned, they create unexpected forwarding paths.

**Mitigation:**  
- Ensure SRv6 locator prefixes are only advertised in the SRv6 domain (not leaked into general IPv6 routing)
- Audit IPv6 reachability between segments: any IPv6 path to a SID is an SRv6 path
- Consider explicit prefix distribution controls: SID block redistribution only within trusted IGP instances

### Scenario 5: Binding SID Attacks (End.B6.Encaps)

The Binding SID (BSID) is a SID that represents an entire SR Policy. When a packet is destined to a BSID, the node holding that BSID encapsulates the packet with a new SRH representing the full policy and steers it along the SR Policy's active candidate path.

**Why BSIDs are high-value attack targets:**

A BSID implementing `End.B6.Encaps` (RFC 8986 §4.13) accepts an inner packet and re-encapsulates it with a new outer SRv6 header. An attacker who can reach a BSID:
1. Causes the binding node to add a new SRH that the attacker didn't write directly — the new SRH is derived from the policy, which the attacker doesn't control
2. However, the inner payload is the attacker's packet — the BSID node is now an SRv6 headend forwarding attacker-controlled traffic through the SR Policy path
3. This may give the attacker access to VPN tables, traffic engineering paths, or network segments that the BSID's SR Policy reaches

**Mitigation:**
- Apply RFC 8754 §5.1 boundary filtering to BSIDs the same as all other SIDs — BSIDs must not be reachable from untrusted sources
- Treat `End.B6.Encaps` SIDs with particular caution — audit which BSIDs are instantiated and what SR Policies they trigger
- Do not expose BSIDs in BGP-SR Policy advertisements to untrusted peers

---

### Scenario 6: Extension Header Fragmentation Bypasses

IPv6 fragmentation uses a separate extension header (Fragment Header, Next Header 44). When combined with SRH, fragmentation can create scenarios where security filters inspect only the first fragment and pass subsequent fragments unchecked.

**The bypass mechanism:**
- An attacker sends a fragmented IPv6 packet where the first fragment contains the IPv6 header and just enough of the SRH to be under the filter's minimum parse length
- The SRH `routing-type 4` field may fall in the second or later fragment
- Some ACL engines only inspect the first fragment's extension header chain — subsequent fragments are passed based on the 5-tuple (source IP, destination IP, protocol) match of the first fragment, without seeing the full SRH

**Detection and mitigation:**
- Verify your ACL hardware's behavior with fragmented SRH packets — test with a known-deny SRH in a fragmented packet
- Cisco recommendation (and common SP practice): deny all IPv6 fragmented traffic at untrusted ingress. Legitimate SRv6 traffic within a properly designed domain should not be fragmented
- `ipv6 access-list BLOCK_FRAGMENTS: deny ipv6 any any fragments` (IOS-XR)
- Junos: `from is-fragment; then discard;` in the iACL (note: `fragment-offset` is an inet/IPv4-only match — for `family inet6`, use `is-fragment` on Trio-based MX, or match `next-header fragment` to catch the IPv6 Fragment Header)

---

### Scenario 7: SRH Amplification

**Mechanism:** A carefully crafted SRH with a large Segment List and `Segments Left` set to the maximum can cause a packet to traverse many nodes within the SR domain before delivery. Combined with small packet size, this provides a modest amplification factor compared to simpler DoS vectors. More relevant is the **processing amplification**: each segment endpoint performs a SID lookup, decrements Segments Left, updates the DA — this is more CPU-expensive than plain IPv6 forwarding.

**Real-world risk:** This is a secondary concern because SRH injection from untrusted sources is blocked by the primary iACL. If an attacker is already inside the domain (compromised host), SRH amplification is one of several available attack paths.

**Mitigation:** CoPP/RE-protection (see the [CoPP and Rate Limiting](#copp-and-rate-limiting-for-srh-processing) section) rate-limits SRH processing per source. Boundary ACL eliminates the external injection path.

## Infrastructure ACL Design for SRv6

Infrastructure ACLs (iACLs) protect the control and management plane by filtering traffic directed at the router itself. In SRv6, this extends to protecting SID processing — you don't want arbitrary sources triggering SID lookups on your PEs.

### ACL Structure — Protecting SRv6 Nodes

Per RFC 8754 §5.1, the primary mechanism is **destination-based**: drop traffic arriving from outside your domain that is destined to your SID block. The secondary mechanism is source-based: drop traffic from non-domain sources destined to local SIDs (per-node protection).

These two mechanisms translate to ACLs applied at domain boundary interfaces:

**IOS-XR — IPv6 iACL implementing RFC 8754 §5.1 filtering:**

```
! Your SRv6 locator/SID block — all SIDs assigned to your domain
! Replace fc00::/32 with your actual SRv6 allocation
ipv6 prefix-list SRV6_DOMAIN_SIDS seq 10 permit fc00::/32 le 128

! Domain source prefixes — authorized SRv6 headends/sources
! NOTE: This should be your INTERNAL infrastructure addressing (loopbacks, link networks),
! NOT the SID block itself. In many deployments, SID locators and infrastructure addresses
! use different prefixes. Authorizing the SID block as a source is NOT what RFC 8754 §5.1
! requires — the RFC says validate that sources are from within the SR domain (your internal
! address space), not that sources are from the SID block.
ipv6 prefix-list SRV6_DOMAIN_SOURCES seq 10 permit 2001:db8:infra::/48
ipv6 prefix-list SRV6_DOMAIN_SOURCES seq 20 permit 2001:db8:loopbacks::/48

! PRIMARY control per RFC 8754 §5.1 Level 1:
! Drop traffic DESTINED to SIDs from non-domain sources
! This ACL applied inbound on external-facing (customer/peering) interfaces
ipv6 access-list SRV6_DOMAIN_BOUNDARY_INBOUND
  !
  ! Permit only essential ICMPv6 types (NOT blanket permit)
  ! Packet Too Big (Type 2) — required for PMTUD
  ! Time Exceeded (Type 3) — required for traceroute/diagnostics
  ! Parameter Problem (Type 4) — required for error signaling
  10 permit icmp any any packet-too-big
  11 permit icmp any any time-exceeded
  12 permit icmp any any parameter-problem
  !
  ! NDP is handled by link-local scope; do not permit ND from global unicast
  !
  ! Deny traffic DESTINED to our SID block from outside sources
  ! (RFC 8754 §5.1 Level 1 — primary boundary protection)
  20 deny ipv6 any fc00::/32
  !
  ! Permit all other IPv6
  30 permit ipv6 any any

! SECONDARY control per RFC 8754 §5.1 Level 2:
! Per-node — also block SRH-bearing traffic from non-domain sources
! This is defense-in-depth, not the primary control
ipv6 access-list SRV6_PER_NODE_INBOUND
  !
  10 permit icmp any any packet-too-big
  11 permit icmp any any time-exceeded
  12 permit icmp any any parameter-problem
  !
  ! Permit SRv6 from authorized internal sources (legitimate intra-domain traffic)
  ! Use infrastructure addressing, not SID block, for source validation
  20 permit ipv6 SRV6_DOMAIN_SOURCES any routing-type 4
  !
  ! Deny SRH-bearing traffic from non-domain sources
  30 deny ipv6 any any routing-type 4
  !
  40 permit ipv6 any any

! Apply BOUNDARY ACL on external-facing interfaces
interface TenGigE0/0/0/0.100
  ipv6 access-group SRV6_DOMAIN_BOUNDARY_INBOUND ingress
```

**Key caveat:** The `routing-type` keyword for IPv6 ACLs in IOS-XR is hardware- and release-dependent. This keyword is **not universally available** — on many platforms (NCS 5500, NCS 540, ASR 9000 with older line cards) it is not recognized and the ACE will fail to commit. The keyword name may differ by release (`routing-type`, `extension-header`, or `ipv6-extension-header`). **The destination-based filter (`deny ipv6 any fc00::/32`) in the boundary ACL is the reliable, universally-supported approach** and matches the RFC 8754 §5.1 primary mechanism. The `routing-type` match in the per-node ACL is aspirational on platforms that support it — always validate ACL behavior with a known-deny test pattern before trusting it in production. If your platform does not support extension header matching in ACLs, rely on the boundary destination-based filter as your primary control.

**Junos — IPv6 iACL with SRH filtering:**

```
# Firewall filter to control SRH-bearing IPv6 traffic
# Applied at the routing-instance or interface level

policy-options {
    prefix-list SRV6_DOMAIN_SOURCES {
        fc00::/32;
    }
    prefix-list SRV6_AUTHORIZED_PEERS {
        /* Add authorized transit/peer SRv6 sources here */
    }
}

firewall {
    family inet6 {
        filter SRV6_IACL_INBOUND {
            interface-specific;

            term PERMIT_ICMP_ESSENTIAL {
                from {
                    next-header icmpv6;
                    icmp-type packet-too-big;
                }
                then accept;
            }
            term PERMIT_ICMP_TIME_EXCEEDED {
                from {
                    next-header icmpv6;
                    icmp-type time-exceeded;
                }
                then accept;
            }
            term PERMIT_ICMP_PARAM_PROBLEM {
                from {
                    next-header icmpv6;
                    icmp-type parameter-problem;
                }
                then accept;
            }

            term PERMIT_SRV6_FROM_DOMAIN {
                from {
                    source-prefix-list {
                        SRV6_DOMAIN_SOURCES;
                    }
                    extension-header routing-header;
                    routing-header-type 4;
                }
                then accept;
            }

            term DENY_SRH_UNTRUSTED {
                from {
                    extension-header routing-header;
                    routing-header-type 4;
                }
                then {
                    discard;
                    count SRH_UNTRUSTED_DROPS;
                    syslog;
                }
            }

            term PERMIT_ALL_OTHER {
                then accept;
            }
        }
    }
}

interfaces {
    xe-0/0/0 {
        unit 100 {
            family inet6 {
                filter {
                    input SRV6_IACL_INBOUND;
                }
            }
        }
    }
}
```

**Important Junos caveat:** The `extension-header routing-header` and `routing-header-type` match conditions are supported on MX series with Trio chipset (MPC3/4/5/6/7/10). On older MPCs or EX/QFX platforms, extension header matching is not supported in hardware and the filter will not compile. Always verify platform capability before deploying. Junos will return an error at commit if the hardware doesn't support the match condition — which is better behavior than silently ignoring it.

**`routing-header-type` availability note:** The `routing-header-type` match condition is supported within firewall filters using `extension-header routing-header` on Trio-based MX platforms starting in Junos OS 18.1. If your platform does not support this granularity, filter on `extension-header routing-header` alone (matching all routing header types) as a safe fallback — this blocks RH Type 0 (deprecated), RH Type 2 (Mobile IPv6), and RH Type 4 (SRv6), which is an acceptable trade-off on most SP edge interfaces where none of those should arrive from untrusted sources.

### Protecting the SID Block — Destination-Based Filtering

Beyond source-based filtering at ingress, consider filtering based on the destination SID block at peering and upstream handoffs. You don't want externally-originated traffic with your SID block in the Destination Address (indicating they're trying to trigger SID processing on your nodes).

**IOS-XR — Block SID-destined traffic from non-domain sources at upstream peers:**

```
! Your SRv6 locator block
ipv6 prefix-list MY_SRV6_LOCATOR_BLOCK seq 10 permit fc00:0::/32 le 128

! On upstream eBGP-facing interfaces — deny traffic toward your SID block from outside
! NOTE: Do NOT add a "permit ipv6 fc00:0::/32 any" rule here. On an upstream INGRESS
! ACL, permitting traffic sourced from your SID block creates a spoofing vulnerability —
! an attacker can forge a source address inside your SID block and match the permit.
! Return traffic is handled by stateful inspection or the egress path, not by source-based
! permits on ingress.
ipv6 access-list UPSTREAM_INGRESS_FILTER
  ! Deny traffic TO your SID block from outside (primary SRv6 protection)
  10 deny ipv6 any fc00:0::/32
  ! Permit everything else
  20 permit ipv6 any any
```

This is conceptually similar to Unicast Reverse Path Forwarding (uRPF) for SRv6 — don't accept traffic destined to your SID space from sources outside your domain.

### HMAC TLV Deployment

RFC 8754 §2.1.2 defines the HMAC TLV as an optional integrity mechanism. When deployed:
- The headend computes an HMAC over the SRH (using a shared key between headend and endpoint)
- The endpoint verifies the HMAC before processing the SID
- Any modification of the SRH in transit (adding, removing, or changing segments) invalidates the HMAC

**Why it's not widely deployed:**

1. **Key distribution** — HMAC requires every headend to share keys with every segment endpoint. At SP scale with hundreds of PEs, this is a key management problem. IPsec has ISAKMP/IKE. SRv6 HMAC has no equivalent automated key distribution mechanism. You're looking at manual key deployment or a custom KMS integration.

2. **Performance cost** — Computing and verifying HMAC at line rate on every SRv6 packet is expensive. ASIC support for HMAC TLV is not universal.

3. **Not always needed** — If your SRH filtering is solid (untrusted SRH dropped at domain edges), HMAC is defense-in-depth rather than the primary mechanism. Most SP deployments prioritize filtering over HMAC and treat HMAC as aspirational.

**Where HMAC makes sense:** High-security environments where you also have SRv6-based service chaining (SFC) that routes traffic through security appliances, and you need assurance that the service chain hasn't been tampered with. HMAC provides that assurance.

## SRH Flavor Security Implications (PSP / USP / USD)

RFC 8986 defines three optional SRH endpoint behaviors that affect how the SRH is handled at the final or penultimate node. Each has security implications that an SP architect needs to understand.

### PSP — Penultimate Segment Pop

**What it does:** When the penultimate segment endpoint processes the SRH, it removes the SRH entirely before forwarding to the ultimate node. The ultimate node receives a plain IPv6 packet (no SRH, no routing header extension).

**Security implications:**
- **Audit and forensics impact:** The SRH — which contains the full forwarding path — is stripped before the final hop. If the ultimate node is an IDS, DLP appliance, or logging collector, it will not see the SRH. The packet appears as plain IPv6 destined to the final address. You lose the full path record at the last node.
- **Firewall interaction:** A firewall sitting between the penultimate node and the ultimate node inspects a plain IPv6 packet, not an SRH packet. If your firewall policy decision depends on knowing whether this was an SRv6 encapsulated flow, PSP hides that.
- **When to require vs prohibit PSP:** If your security architecture requires full SRH visibility at every inspection point, PSP must be disabled or inspection points must be placed before the penultimate node. If SRH forensics are not required at the final hop (and you want reduced header overhead), PSP is safe.

### USP — Ultimate Segment Pop

**What it does:** The ultimate segment endpoint removes the SRH after processing. Similar to PSP but at the final node, not the penultimate.

**Security implications:**
- Less impactful than PSP since the SRH has already been fully processed before removal — the ultimate node has already verified the segment. USP mostly affects whether downstream applications on the same host or inline tap see the SRH.
- If you have application-layer analysis tools on the segment endpoint, they will not see the SRH after the dataplane strips it.

### USD — Ultimate Segment Decapsulation

**What it does:** After the endpoint processes its SID (typically an END.DX or END.DT variant), it decapsulates the SRv6 outer header entirely and delivers only the inner payload to the next hop.

**Security implications:**
- **VPN boundary clarity:** END.DT4 and END.DT6 decapsulate at VRF boundaries — this is intentional and the boundary point is where you insert your VPN edge policy.
- **Double-encapsulation blind spots:** If the inner payload is itself encapsulated (GRE, IPsec, another SRv6 flow), the decapsulated delivery hands an opaque payload to the VRF. Your inspection must happen at the decapsulation point, not downstream.
- **Spoofing risk via END.DT:** An attacker with SRH injection access who reaches an END.DT SID can deliver arbitrary inner packets into a specific VRF. This is the "VRF key" attack mentioned in RFC 8986 — SIDs exposing END.DT functions are high-value targets for injection. Audit which END.DT SIDs are instantiated and on which nodes; each one is a VPN insertion point if SRH injection is not filtered.

**Bottom line on flavors:** The security implication of PSP/USP/USD is primarily about **where in the path** your inspection and logging occur. Design your monitoring architecture with the SRH lifecycle in mind — the SRH is progressively stripped as the packet traverses the SR domain.

## CoPP and Rate Limiting for SRH Processing

SRH processing is router-CPU-adjacent on most platforms — even hardware-accelerated SRv6 forwarding involves SID table lookups, HMAC verification (if deployed), and policy enforcement that has more overhead than plain IP forwarding. This creates a resource exhaustion attack surface.

**The threat:** A packet flood with crafted SRH headers directed at an SRv6-capable PE can exhaust:
- SID table lookup capacity (software hash table or TCAM)
- HMAC verification CPU cycles (if HMAC is enabled)
- Punt queue bandwidth (packets requiring software handling that can't be hardware-forwarded)

**CoPP conceptual approach for SRv6 (illustrative — syntax varies by release):**

The exact CoPP/LPTS configuration syntax for SRv6 varies across IOS-XR releases and platforms. The following example illustrates the *conceptual approach*: classify SRv6-destined traffic, rate-limit it, and keep it separate from your general CoPP policy. **Do not copy-paste this into production without validating against your specific platform and release.**

```
! IOS-XR — CONCEPTUAL CoPP approach for SRH-directed traffic
! Syntax shown below is illustrative. Exact class-map/policy-map syntax,
! attachment method, and LPTS vs CoPP framework differ across releases.
!
! The key principle: classify SRv6 traffic destined to local SIDs,
! rate-limit it separately from other control-plane traffic.

! Step 1: Classify SRv6 traffic via ACLs
ipv6 access-list SRV6_DEST_LOCAL
  ! Packets destined to locally-instantiated SRv6 SIDs
  10 permit ipv6 any <your-local-locator-prefix>/48
!
ipv6 access-list SRH_EXCEPTION
  ! Packets triggering SRH exception handling
  ! Note: 'routing-type 4' keyword availability varies by platform/ASIC
  10 permit ipv6 any any routing-type 4

! Step 2: Build class-map referencing ACLs
class-map match-any SRH_PROCESSING
  match access-group ipv6 SRV6_DEST_LOCAL
  match access-group ipv6 SRH_EXCEPTION
  end-class-map

! Step 3: Apply rate limit in policy-map
policy-map CoPP_SRV6
  class SRH_PROCESSING
    police rate 10000 pps burst 5000 packets
      conform-action transmit
      exceed-action drop
  class class-default
  end-policy-map

! Step 4: Attach to control plane
! Attachment method varies — some platforms use 'control-plane' hierarchy,
! others use LPTS framework. Consult platform-specific documentation.
```

**Junos — Routing Engine protection with SRH rate limit (applied to `lo0`):**
```
firewall {
    family inet6 {
        filter PROTECT_RE_SRV6 {
            term RATE_LIMIT_SRH_TO_RE {
                from {
                    extension-header routing-header;
                    routing-header-type 4;
                    destination-prefix-list {
                        /* Define this prefix-list with your local SRv6 locator SIDs */
                        LOCAL_SRV6_SIDS;
                    }
                }
                then {
                    policer SRH_RE_POLICER;
                    accept;
                }
            }
            term DEFAULT_DENY_SRV6 {
                from {
                    extension-header routing-header;
                    routing-header-type 4;
                }
                then {
                    discard;
                    count SRH_REJECTS;
                }
            }
            term ACCEPT_ESTABLISHED {
                /* Your existing RE protection terms go here */
                then accept;
            }
            /* NOTE: This filter should be part of a default-deny lo0 filter.
               The 'accept' in RATE_LIMIT_SRH_TO_RE only fires for SRH traffic
               to known local SIDs. Unknown SRH traffic hits DEFAULT_DENY_SRV6.
               Do NOT add a blanket 'then accept' default term. */
        }
    }
    policer SRH_RE_POLICER {
        if-exceeding {
            bandwidth-limit 10m;
            burst-size-limit 1500000;
        }
        then {
            discard;
        }
    }
}
```

**Key principle:** Apply CoPP/RE-protection specifically for traffic destined to your local SID block. This is separate from the boundary ACL (which drops external SRH traffic entirely) — CoPP rate-limits the legitimate-but-high-volume case where your own domain generates more SRH processing than the control plane can handle.

## AH Header Compatibility (RFC 8754 §7.5)

RFC 8754 §7.5 addresses the interaction between the SRH and IPsec Authentication Header (AH). The RFC states that **the use of SRH with AH is not defined in this document** and that future documents may define it. In practice, operators should not assume AH protects SRH semantics.

**Why AH is problematic with SRH:**

AH provides integrity protection by computing an HMAC over the IP header and payload, covering all fields that are not expected to change in transit (mutable fields are zeroed during computation). The challenge with SRv6 is that segment endpoint processing *modifies* the Destination Address to advance to the next SID — the endpoint sets the DA to a value that was not the original DA covered by the HMAC. When the next node performs AH verification, the integrity check fails because the DA has been changed to a value not covered by the original HMAC computation.

RFC 8754 §7.5 does not say "AH is incompatible" in absolute terms — it says the interaction is **undefined** and that the SR domain does not rely on AH to secure the SRH. The practical takeaway is the same: do not use AH with SRv6.

**What this means operationally:**

- If you have legacy infrastructure that uses AH for certain traffic flows and you're introducing SRv6 over the same path, those flows will not work with SRv6 encapsulation.
- AH is not a substitute for the HMAC TLV (which is SRH-aware and specifically designed for SRH integrity).
- For SRv6 path integrity, use the HMAC TLV (RFC 8754 §2.1.2).
- For payload encryption/integrity, use IPsec ESP (not AH) — ESP is compatible because it encrypts the payload and does not cover the mutable IPv6 DA header.

**IE exam relevance:** This is a topic that discriminates between candidates who have read the RFC and those who haven't. The question "can you protect an SRv6 path with IPsec?" has a nuanced answer: ESP yes, AH undefined (effectively no). Knowing the *reason* (SRH endpoint processing modifies the DA, breaking AH's integrity model) is the exam-level answer.

### Firewalls and Middleboxes — The Honest Assessment

Most production firewalls do not understand SRv6 SRH semantics in the way they need to for security enforcement. The landscape as of 2026:

**Palo Alto Networks (PAN-OS):**  
PAN-OS inspects IPv6 but its SRv6 awareness is limited. As of PAN-OS 11.x, PAN can parse SRH headers in application identification, but deep SID-based policy enforcement (e.g., "policy decision based on final SID destination, not DA") is not a first-class feature. SRH filtering can be achieved via custom application filters or zone protection profiles targeting RH Type 4, but this requires validation in your specific deployment. Official PAN support documentation is sparse.

**Fortinet FortiGate:**  
FortiOS IPv6 inspection can identify extension headers. SRH-specific policy enforcement (decision-based on SRH segment list) is limited. FortiGate can block routing headers broadly via IPv6 extension header restrictions in zone policies. This is a blunt instrument — blocks all RH types, not just RH4 — but if your use case doesn't need RH Type 2 (MIPv6 Home Address option), blocking all routing headers is a defensible policy.

**The general principle:**  
Any firewall in an SRv6 path that cannot inspect the full SRH and interpret SID behaviors is fail-open for SRv6-based bypasses. Two choices:
1. Ensure the firewall inspects SRH and enforces policy based on full SID behavior semantics (not just the segment list — see the [Firewall Deep Inspection](#firewall-deep-inspection--beyond-segment-list-chasing) section)
2. Block RH Type 4 on the interfaces facing untrusted segments (fail-closed)

**Assume fail-open unless verified.** If you haven't confirmed your firewall correctly parses and enforces policy on SRH traffic for your specific platform and software train, treat it as fail-open and add compensating controls.

## SRv6 vs SR-MPLS: The Honest Security Tradeoff

This comparison matters for SP architecture decisions. People often say "SRv6 is more flexible" without discussing what that flexibility costs in security. Here it is:

| Aspect | SR-MPLS | SRv6 | Winner |
|--------|---------|------|--------|
| **Ethertype visibility** | Unique (`0x8847`), filterable everywhere | Same as IPv6 (`0x86DD`), invisible to most filters | SR-MPLS |
| **Label space scope** | Domain-local. Labels only meaningful within MPLS domain | SIDs are globally routable IPv6 addresses | SR-MPLS |
| **Injection attack surface** | Lower barrier: requires MPLS access, but MPLS-over-UDP (RFC 7510) and MPLS-over-GRE reduce this to IP reachability | Lower barrier: requires only IPv6 reachability to SID block | SR-MPLS (narrower default, not immune) |
| **Firewall support** | Widespread (label matching well-supported) | Sparse. Few firewalls understand SRH semantics | SR-MPLS |
| **Transit node security** | Non-MPLS nodes typically drop MPLS traffic; however, MPLS-over-UDP/GRE is forwarded as IP | Non-SRv6 nodes forward SRH as IPv6 (transparent) | SR-MPLS (for native MPLS; gap narrows with encap) |
| **Hardware ACL support** | Widespread (label matching well-supported) | Limited (extension header matching varies by ASIC) | SR-MPLS |
| **HMAC protection** | Not applicable to MPLS labels; label scope provides domain isolation instead | Available (RFC 8754 §2.1.2) but rarely deployed; verification is optional/policy-driven | SR-MPLS (inherent isolation) vs SRv6 (optional integrity) |
| **SID/label distribution** | IS-IS/OSPF TLVs; routed within domain | IS-IS/OSPFv3 TLVs; SIDs are globally routable | SR-MPLS |
| **Operational simplicity** | Single protocol stack (IP + MPLS) | Single protocol stack (pure IPv6) | Neutral |
| **DPI and forensics** | Well-understood by existing tools | SRH parsing not universal; uSID adds opacity | SR-MPLS |

**The honest summary:** SR-MPLS has stronger *default* security properties because the label space is domain-local. You cannot inject an MPLS label from outside the MPLS domain and have it processed — there's no IP routing path to an MPLS label. SRv6 SIDs are IPv6 addresses — and if you have IPv6 reachability, you can attempt to reach them.

This advantage is not absolute. SR-MPLS has its own attack surface: MPLS-over-UDP (RFC 7510) and MPLS-over-GRE reduce the "label injection requires MPLS access" barrier. VPN label spoofing is possible in some architectures if label allocation is predictable. Inter-AS Option C exposes label exchange to eBGP. So the accurate statement is that SR-MPLS requires *less* explicit security configuration to achieve a defensible baseline — not that it is immune to attack by design.

SRv6 requires explicit security design that SR-MPLS gets partly for free from its domain-local label semantics. The firewall, ACL, and monitoring investments required for a secure SRv6 deployment are higher than for SR-MPLS. That cost is worth it for deployments that genuinely need what SRv6 offers (pure IPv6, programmability, no MPLS complexity). It's not worth it if MPLS works fine for your use case.

No marketing material will tell you this. Now you know.

## Encapsulated SRv6 — GUE and SRv6-over-UDP Security

Not all SRv6 deployments use native IPv6 extension headers. Some use encapsulation tunneling:

**SRv6 over GUE (Generic UDP Encapsulation):**
RFC 9343 defines SRv6 over GUE, which encapsulates SRv6 packets inside a UDP tunnel. This has security implications:
- The SRH is hidden inside a UDP payload — firewalls and ACL engines that don't decapsulate GUE cannot inspect the SRH at all
- The outer header is standard UDP (protocol 17), which is permitted through most firewalls by default
- GUE decapsulation points become trust boundaries — the decapsulating node must validate the inner SRH before processing
- If you deploy both native SRH and GUE-encapsulated SRv6, your ACL strategy must account for both paths

**SRv6 over UDP (direct encapsulation):**
Some implementations encapsulate SRv6 directly in UDP without GUE headers (using destination port as a discriminator). The same security considerations apply — the SRH is invisible to middleboxes until decapsulation.

**Operational guidance:**
- If you use encapsulated SRv6, apply the same RFC 8754 §5.1 filtering principles at the decapsulation boundary
- Decapsulation nodes must perform source validation on the inner SRv6 header, not just the outer encapsulation header
- Monitor for unexpected GUE/UDP-SRv6 traffic on interfaces where you don't expect it
- ACLs should block UDP traffic to your decapsulation endpoints from untrusted sources (similar to how you block SRH from untrusted sources for native SRv6)

## Recommended Security Architecture

A production SRv6 backbone with a defensible security posture needs all of the following. Missing any one of these is a gap.

### Layer 1: Domain Edge Filtering

Per RFC 8754 §5.1, every external-facing interface must implement two levels of control:

**Level 1 (Primary — destination-based):** Drop any packet arriving from outside the domain that is destined to an address within your SRv6 SID block. This is the boundary control — your SIDs should never be reachable from external networks. *(Note: the "Level 1/Level 2" labels used here are a pedagogical framework for this guide, not terminology from RFC 8754 itself. The RFC describes both controls without numbering them.)*

**Level 2 (Secondary — per-node source+destination):** Each SRv6-capable node drops packets destined to its local SIDs when the source is not within the SR domain. This catches attacks that bypass the boundary (compromised internal hosts).

Both levels should also log drops for incident detection. The ACL example in the Infrastructure ACL section above implements both levels.

### Layer 2: SID Source Validation

Per RFC 8754 §5.1 Level 2, each SRv6-capable PE should drop packets destined to its local SIDs from sources outside the SR domain. This is implemented via per-interface iACLs or per-node firewall filters (see the ACL examples in the Infrastructure ACL section). Both platforms enforce this through ACL configuration — there is no single "enable SID source validation" knob. Apply the `SRV6_PER_NODE_INBOUND` ACL (or Junos equivalent) on all interfaces that may receive SRv6 traffic, not just external-facing ones.

This is defense-in-depth behind the edge ACL. If an attacker bypasses the edge (compromised internal host, rogue device), per-node ACLs are the second line.

### Layer 3: SID Allocation Hygiene

- Use a dedicated, non-overlapping SRv6 block separate from your operational IPv6 addresses
- Don't advertise the SRv6 block into public BGP — keep it internal (no-export community at a minimum)
- Assign opaque function values — don't use sequential integers that make enumeration trivial
- Maintain a SID registry (spreadsheet at minimum, IPAM integration ideally) — know what every SID does and who owns it
- Audit SID table periodically: SIDs should match your registry; unexpected SIDs indicate a misconfiguration or unauthorized allocation

### Layer 4: Monitoring and Detection

Build detection for the attack patterns described above:

**SRH injection detection:**
- Alert on SRH-bearing packets that match your drop ACL (source outside trust domain)
- Baseline normal SRH volume; alert on significant increases
- Monitor SID lookup failures: SIDs that arrive but don't match the local SID table indicate either misconfiguration or injection attempts

**Topology reconnaissance detection:**
- Monitor for ICMP probes sweeping your SRv6 locator block
- Alert on ICMP TTL-exceeded responses from backbone nodes destined to external addresses (may indicate traceroute-based mapping)

**OAM tool misuse for reconnaissance:**
SRv6 OAM mechanisms (RFC 9259 and related) — including SRv6 `ping`, `traceroute`, and STAMP/TWAMP session measurement — are operational tools that attackers can repurpose for reconnaissance:
- An attacker with IPv6 reachability to your SID block can use SRv6 traceroute to map the exact segment list through your backbone — revealing node order, adjacency relationships, and path diversity
- OAM packets crafted with specific SID sequences can test whether a path exists, whether a SID is active, and what behavior is bound to it — without triggering data-plane delivery
- STAMP/TWAMP reflectors bound to SRv6 SIDs can be abused to confirm liveness and latency characteristics of internal infrastructure
- **Mitigation:** Apply the same RFC 8754 §5.1 filtering to OAM-destined traffic as to all other SRv6 traffic. OAM SIDs are still SIDs — they should not be reachable from untrusted sources. Rate-limit OAM responses per source to prevent rapid topology enumeration. Log unexpected OAM sessions directed at your SID block from external sources.

**Relevant telemetry paths:**
```
# IOS-XR — SRv6 SID counters
Cisco-IOS-XR-segment-routing-srv6-oper:srv6/active/locators/locator/sid-table

# IOS-XR — ACL counters (including SRH drops)
Cisco-IOS-XR-es-acl-oper:es-acl/active/oper-summary

# Junos — SRv6 SID statistics
/junos/spring/srv6/sid-table/entry

# Junos — Firewall filter counters (for SRH drop counting)
/junos/firewall/
```

### Layer 5: Incident Response Preparation

Before you need it, prepare:

1. **Packet capture tooling for SRH:** Confirm that your capture tools (Wireshark, tcpdump, network TAPs) decode SRH correctly. Wireshark has supported RH Type 4 since version 3.4. tcpdump displays extension headers but doesn't label SRH semantics by default. Test before the incident.

2. **SRH-aware forensics:** If you have an incident involving SRv6 forwarding, you need to trace the segment list. Establish which commands give you SID forwarding history and path verification:
   ```
   # IOS-XR — trace SRv6 packet
   traceroute srv6 policy name <policy-name>
   
   # Junos — SRv6 path verification
   ping fc00:0:pe7:dt4::100:1 routing-instance default source fc00:0:pe1:e001::
   ```

3. **Document your SID-to-function mapping:** During an incident, you'll be reading SIDs in packet captures. If you don't have a lookup table for `fc00:0:pe7:e010::` → "END.DT4 at PE7, VRF customer-100," you're decoding hex during an outage. Pre-build this reference.

## uSID (Micro-SID) Security Considerations

uSID (RFC 9602 §3) compresses multiple SIDs into a single 128-bit IPv6 address, trading transparency for efficiency. This has specific security implications:

- **ACL opacity:** uSID-compressed addresses look like unusual but valid IPv6 addresses. ACL rules written for full SRv6 SIDs (e.g., `deny ipv6 any fc00::/32`) still match uSID traffic because the locator prefix is preserved. However, per-function or per-SID filtering within a uSID block is significantly harder — the function bits are packed into the same 128-bit address, and parsing them requires uSID-aware hardware or software.
- **Flow visibility:** NetFlow/IPFIX collectors that don't understand uSID structure will log compressed addresses without decomposing the SID list. This reduces forensic granularity — you lose the ability to trace individual hops from flow records.
- **Enumeration resistance:** uSID actually *improves* enumeration resistance compared to uncompressed SIDs, because the compressed format makes it harder to identify individual function assignments by probing. The trade-off is that you also can't easily identify what a uSID does from a packet capture without a decoder.
- **ACL recommendation:** Filter on the uSID locator prefix (the /48 or /64 block) rather than attempting per-function matching. This is the same recommendation as for uncompressed SRv6 — filter on the locator block at domain edges.

## Control-Plane Attack Surface

This section focuses on attacks on the *control plane* that provisions SRv6 — not the data-plane injection attacks covered in the scenarios above. If an attacker can compromise the control plane, many data-plane defenses become irrelevant.

### IGP Locator Advertisement Poisoning

SRv6 locators are advertised via IS-IS or OSPFv3 extensions (IS-IS SRv6 TLVs, OSPFv3 SRv6 Extended Prefix Opaque LSAs). A rogue router or compromised IGP adjacency can inject fraudulent locator advertisements:

- **Fake locator injection:** Advertise a locator prefix that overlaps with or replaces a legitimate SRv6 locator. Traffic destined to the real locator is hijacked to the attacker's node.
- **Locator withdrawal attack:** Withdraw legitimate locator advertisements, causing blackholes for SRv6 traffic to those nodes.
- **SID behavior spoofing:** Advertise incorrect SRv6 Endpoint behavior codepoints (e.g., advertise `End.DT4` with a table ID that shouldn't be exposed). Downstream nodes may steer traffic based on the false advertisement.

**Mitigation:**
- IS-IS/OSPFv3 authentication (MD5 or stronger) on all adjacencies — non-negotiable in SRv6 deployments
- Segment routing prefix SID authorization via IGP policies where platforms support them
- Monitor for unexpected locator advertisements via telemetry (compare running SID table against planned SID registry)

### BGP SR Policy Abuse

BGP SR Policy (draft-ietf-idr-segment-routing-te-policy) distributes SR Policies via BGP. If an attacker can inject or modify BGP SR Policy advertisements:

- **Policy injection:** Advertise a malicious SR Policy with a BSID that redirects traffic through attacker-controlled paths
- **Policy hijack:** Modify an existing policy's candidate path to route through compromised nodes
- **BSID collision:** Advertise a BSID that conflicts with an existing BSID, causing unpredictable steering

**Mitigation:**
- BGP session security: MD5/TCP-AO on all BGP sessions carrying SR Policy AFI/SAFI
- Route filtering: Only accept SR Policy NLRI from authorized BGP peers (prefix-lists, AS-path filters, BGP communities)
- BSID allocation monitoring: Alert on BSID conflicts or unexpected BSID advertisements

### Internal Compromised Headend

A trusted internal SRv6 headend (a PE or router with SRv6 encapsulation capability) that is compromised can generate perfectly valid SRH or no-SRH traffic. This is a fundamentally different threat than external injection:

- Traffic originates from legitimate infrastructure addresses (passes source validation)
- SRH is well-formed (passes any HMAC validation if the compromised node has valid keys)
- The attack is invisible to boundary ACLs because it originates inside the trust domain

**Mitigation:**
- Per-node rate limiting (CoPP/LPTS) constrains the volume of SRH processing any single node can demand
- Network behavior analytics: detect unusual SRv6 traffic patterns from any single headend
- RFC 8754 §5.2 delegated validation model: in environments where hosts originate SRv6 (DC/DCI), validate that the host is authorized to use the SIDs it's injecting

## Inter-Domain and Multi-AS SRv6 Security

RFC 8754 defines the SR domain as a trusted administrative boundary. In practice, SRv6 deployments don't always stay neatly inside one AS. Inter-AS SRv6 — whether for traffic engineering, service chaining, or DCI — changes the security model in ways that single-domain guidance doesn't cover.

### The Boundary Problem at Scale

When SRv6 crosses AS boundaries, the "trust domain" is no longer a single IGP area or AS. The locator prefixes of AS-A are now reachable (and potentially reachable to SRv6-capable nodes) in AS-B. If AS-B has SRv6-capable nodes, they can process AS-A's SIDs — even if that was never intended.

**The core tension:** RFC 8754 §5.1 assumes you control both sides of the boundary. In inter-AS deployments, you control one side. The other side's security posture becomes your exposure.

### Inter-AS Option C — Label (and SID) Exchange

Inter-AS Option C (RFC 4364 §10, often called "labeled unicast") exchanges VPNv4/VPNv6 next-hop reachability with labels across AS boundaries. In an SRv6 context, the equivalent is exchanging SRv6 SID reachability — the remote AS's locator prefixes become reachable in your IGP/BGP table.

This means:
- **Locator prefix leakage** — Your SRv6 locators may be advertised to peer ASes. If they're not properly filtered, external ASes can send traffic directly to your SIDs.
- **BSID exposure** — If BGP SR Policies (draft-ietf-idr-segment-routing-te-policy) are exchanged across AS boundaries, BSIDs from one domain may be reachable from another. A misconfigured eBGP session can expose high-value BSIDs to peers.
- **End.DT/End.DX exposure** — VPN service SIDs that should only be reachable from within your AS may be reachable from peer ASes if locator prefixes are leaked.

**Mitigation:**
- Apply RFC 8754 §5.1 filtering at AS boundaries — treat the inter-AS link the same as any external interface. Drop traffic destined to your SID block arriving from eBGP peers.
- Use BGP communities and route filtering to prevent locator prefix advertisement beyond intended scope.
- Never exchange BSIDs across AS boundaries unless you explicitly intend cross-AS SR Policy stitching.

### Multi-AS SRv6 Stitching

Some architectures use SRv6 to stitch paths across multiple ASes — an SR Policy in AS-A connects to an SR Policy in AS-B via a "stitching" SID at the ASBR. This creates an interesting trust model:

- The stitching SID at the ASBR is the trust boundary — it must validate incoming SRv6 traffic from the peer AS before encapsulating it into the domestic SR Policy.
- The peer AS's SR Policy internals (full segment list) should not be visible or meaningful inside your AS — the stitching SID should re-encapsulate with your own SR Policy.
- If the stitching SID is an `End.B6.Encaps`, it acts as a security gateway — accepting traffic from the peer and binding it to an internal policy. This is the correct model.
- If the stitching is transparent (the peer's SRH passes through unmodified), you've leaked internal topology into the peer's control. Don't do this.

### Practical Inter-Domain Recommendations

1. **Filter locator prefixes at AS boundaries.** Your SID block should not be reachable from external ASes unless you explicitly design for inter-AS SRv6.
2. **Use stitching SIDs, not transparent SRH forwarding.** When SRv6 must cross AS boundaries, the ASBR should re-encapsulate — don't expose internal segment lists to peers.
3. **Audit eBGP sessions for SR Policy NLRI.** If you're exchanging BGP SR Policy AFI/SAFI with peers, know exactly which BSIDs are being advertised and filter aggressively.
4. **Treat the inter-AS link as untrusted.** Apply the same iACL model (destination-based SID block filtering, source validation) at ASBR interfaces as you would at customer-facing interfaces.

## Extension Header Chain Evasion

Scenario 6 covers fragmentation-based evasion of SRH inspection. There is a related but distinct evasion technique using **deep extension header chains**.

**The mechanism:**
IPv6 allows chaining multiple extension headers before the upper-layer payload. An attacker can craft a packet with a long chain of Hop-by-Hop Options, Destination Options, and Routing Headers before the SRH:

```
IPv6 Header → Hop-by-Hop → Dest-Opts → RH Type 0 (invalid) → Dest-Opts → RH Type 4 (SRH) → Payload
```

ACL hardware and firewalls have limited parsing depth — they read N bytes into the packet to locate and classify extension headers. If the SRH falls beyond the parser's maximum parse depth, the device:
- Cannot match on `routing-type 4` (it never reaches the SRH)
- May classify the packet as "has extension headers" or may treat it as unknown
- Will typically forward it as IPv6 based on the Destination Address

**This is not theoretical.** Many ASIC generations have documented maximum EH parse depths (typically 4-8 extension headers). Beyond that depth, header matching degrades or stops.

**The specific risk for SRv6:**
- An attacker who knows (or guesses) your ACL hardware's parse depth can pad the EH chain to push the SRH below the parse threshold
- Your `routing-type 4` filter silently fails to match — the packet passes
- Destination-based filtering (`deny ipv6 any fc00::/32`) still catches it, because the parser can always read the IPv6 DA from the fixed base header

**This is another reason destination-based SID block filtering is the primary control.** Extension header matching — whether `routing-type 4`, `extension-header routing-header`, or any EH-based filter — is inherently depth-limited. The IPv6 DA is always in the same place.

**Mitigation:**
- Prefer destination-based SID block filtering over EH-type matching
- Some platforms allow configuring a maximum EH chain length or dropping packets with excessive EH chains (IOS-XR: platform-specific; Junos: `ba-led-ingress-limits` or similar platform knobs)
- RFC 9288 recommends dropping packets with unknown or excessive extension headers at transit routers — this catches deep EH chains as a side effect

## SID Behavior Risk Hierarchy

Not all SIDs carry equal risk. Understanding which SID behaviors are most dangerous helps prioritize monitoring and protection:

| Risk Level | SID Behaviors | Why Dangerous |
|-----------|--------------|--------------|
| **Critical** | `End.DT4`, `End.DT6`, `End.DT46` | Decapsulate and inject into specific VRF tables. An attacker reaching these SIDs can deliver arbitrary packets into any VPN table the SID is bound to — effectively a "VRF key." |
| **Critical** | `End.B6.Encaps`, `End.B6.Encaps.Red` | Binding SIDs that trigger entire SR Policies. An attacker can use the BSID as a gateway to steering paths they didn't construct, forwarding attacker traffic through legitimate policies. |
| **High** | `End.DX4`, `End.DX6`, `End.DX2` | Cross-connect SIDs that deliver to specific next-hops or L2 bridges. Less scope than DT variants but still allow traffic injection to specific adjacencies. |
| **Medium** | `End.X`, `End.T` | Adjacency/topology SIDs that steer to specific links or IGP areas. Useful for path manipulation but don't directly access VPN tables. |
| **Lower** | `End` (basic) | Pure forwarding — decrement SL, update DA. No decapsulation, no VRF injection, no policy binding. Still useful for path manipulation but limited in direct damage. |

**Operational takeaway:** Prioritize monitoring and protection around `End.DT*` and `End.B6*` SIDs. These are the highest-value targets for an attacker. If you have limited resources for SID auditing, start with these behaviors.

## Firewall Deep Inspection — Beyond Segment-List Chasing

The firewall bypass scenario (Scenario 3) describes firewalls that only see the IPv6 DA, not the full segment list. But even a firewall that parses the full SRH segment list **cannot reliably determine the security effect** of SRv6 traffic from the segment list alone. Here's why:

The final outcome of an SRv6 packet depends on the **local behavior bound to the SID**, not just the SID value:
- An `End.DT4` SID with table ID 100 delivers into VRF-100. The SID value itself doesn't tell you this unless you have the SID-to-behavior mapping.
- An `End.B6.Encaps` SID triggers a completely new SR Policy that the firewall can't see inside.
- PSP/USP stripping means the segment list may be incomplete at the inspection point.

**Practical guidance for firewalls in SRv6 paths:**

1. **SRv6-aware firewalls** must understand RH Type 4 + local SID semantics — not just parse the segment list. This requires the firewall to have a SID behavior table or integration with the SRv6 controller.
2. **Non-SRv6-aware firewalls** should fail closed: block RH Type 4 at the segment boundary. This is the safer default.
3. **Assume fail-open unless verified.** If you haven't confirmed your firewall correctly interprets SRH and SID behaviors for your specific platform and software train, treat it as fail-open and add compensating controls.

## Fragmentation Filtering — Tradeoffs, Not Absolutes

Scenario 6 recommends denying fragmented IPv6 traffic at untrusted ingress. This is a common and effective hardening measure, but it is not free of operational cost:

**Benefits:**
- Eliminates the fragmentation-based SRH bypass (RH Type 4 in non-first fragment)
- Reduces evasion surface for extension-header-based attacks
- Simplifies ACL evaluation (no need for fragment reassembly logic)

**Risks of blanket fragment drops:**
- Breaks legitimate IPv6 flows when Path MTU Discovery (PMTUD) is impaired — and PMTUD impairment is common (ICMPv6 Packet Too Big filtered, tunnels reducing MTU without signaling)
- Can break applications that rely on fragmentation (rare in modern networks, but some legacy protocols still fragment)
- If you filter fragments and PMTUD is broken, you get silent blackholes — the worst kind of failure to troubleshoot

**Recommendation:** Treat fragment filtering as a **conditional hardening measure**, not a universal default:

1. Prefer blanket fragment drops on untrusted ingress *if* your environment supports it (PMTUD working, no fragmentation-dependent applications)
2. Validate PMTUD end-to-end before enabling: `ping -s 2000 <destination>` across the filtering boundary
3. If you cannot drop all fragments, at minimum ensure your ACL hardware evaluates extension headers across all fragments, not just the first
4. Monitor for fragmentation events after enabling the filter — an increase in TCP retransmissions or connection failures may indicate PMTUD problems
